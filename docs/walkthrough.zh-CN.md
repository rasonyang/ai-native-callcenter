# 功能走查（管理员 · 坐席 · 班长）

从一个空系统开始：管理员把平台搭起来，坐席接一通电话，班长在看板上确认它。

每一步都写清楚**在哪个页面做**、**做完应该看到什么**。看到的和写的不一样，就是一条缺陷 ——
在那一行下面加一行 `实际：…（时间）`，通话类问题往往要靠时间去日志里对回来。

| | |
|---|---|
| 入口 | `http://127.0.0.1:8080` |
| 登录口令 | `aicc@12345` |
| 话机 | web-sip-phone 浏览器扩展 |
| 话机口令 | 演示数据预置的分机是 `aicc@123`；自己新建的由系统生成，在分机页查看 |

## 前置：把系统跑起来

走查表从「用 admin 登录」开始，前提是下面这些都在跑。**每一项都给了自检命令**——
先把它们都跑通再往下走，否则后面失败的原因会分不清是系统没起还是功能有问题。

所有命令都在**仓库根目录**下跑：

```sh
cd ~/workspaces/github/ai-native-callcenter
```

**系统很可能不是空的。** 开发库里有演示数据（账号 `admin` / `supervisor` / `wei` / `ben`，
号码 95001/95002/95011/95012，队列和一个已发布的流程）。走查第一节说的「从零」是指
**你自己新建一套**并观察建的过程，不是先把已有的删光。新建时用一眼能认出的名字（如
`walkthrough_agent`、`wt_queue`），走完好清理。

| # | 起什么 | 命令 | 自检 |
|---|---|---|---|
| 一 | PostgreSQL 与对象存储 | `docker compose -f deploy/dev/docker-compose.yml up -d` | `docker compose -f deploy/dev/docker-compose.yml ps` 两个服务都 healthy |
| 二 | FreeSWITCH | 本机原生安装，开机常驻 | `/usr/local/freeswitch/bin/fs_cli -x "status"` 输出 `ready` |
| 三 | 业务后端（bot 用） | `go run ./cmd/aicc-mockbackend -addr 127.0.0.1:8770` | `curl -s -X POST 127.0.0.1:8770/api/repair/status -d '{"rmaNo":"RMA1001"}'` 返回 `retCode 000000` |
| 四 | 应用 | `deploy/dev/restart.sh` | 打开 `http://127.0.0.1:8080` 出现登录页 |
| 五 | 话机 | web-sip-phone 浏览器扩展注册 | `/usr/local/freeswitch/bin/fs_cli -x "sofia status profile internal reg"` 里有你的分机 |

几件容易踩的：

- **第三项只有走第四节（Bot 能力）才需要**，第一到第三节不用它。但它必须在**应用启动之前**
  就位并写进 `.env`，因为地址是启动时读的：

  ```
  AICC_BOT_BACKEND_BASE=http://127.0.0.1:8770
  ```

  应用已经在跑才加这一行的话，得重启一次应用才生效。

- **`deploy/dev/restart.sh` 会顺带构建前端**。改过 `web/` 下的东西就必须用它，不能只
  `go build`——界面是编进二进制的（`go:embed web/dist`），只编 Go 会让浏览器继续拿到旧界面。

- **模型供应商**：本机 `.env` 用的是 `AICC_PROVIDER=qwen`，并且需要 `AICC_TRANSCRIBE_ENDPOINT`
  （工作区 id 在主机名里），缺了应用直接拒绝启动。openai 太贵，验证一律走 qwen。

- **每通 AI 电话都在花钱**。第四节的 bot 走查会真实调用模型，走之前想清楚要打几通。

> **先读这一条：中继不在这个界面里新增。**
>
> 中继（网关）定义在 FreeSWITCH 自己的配置文件里，平台只读它的状态，不写它。走查时能做的是
> **确认中继在位** —— 管理员的「概览 → 系统健康」会列出交换机报告的网关。如果那里写着
> 「无 —— 交换机没有报告任何网关」，说明交换机侧还没配好，后面所有对外的呼入呼出都走不通，
> 先停下来处理它。
>
> 你在界面里新增的是**号码**（DID），号码通过交换机已有的中继进出。

## 一 · 管理员：从零把平台搭起来

**这一段的顺序不能打乱。** 账号建好才有坐席身份，坐席配进队列队列才有人，流程发布了号码才有东西可绑。
每一步都依赖前一步的产物，所以这里编了号；后面两个角色是逐屏检查，不是流程，就没有编号。

## 二 · 坐席：签入、接一通、打一通

> **先装话机。** 用 web-sip-phone 浏览器扩展，以第 2 步分到的分机号注册，口令是第 5 步查到的那个。
> 注意**话机注册口令和登录口令不是同一个** —— 注册用的是分机口令，不是 `aicc@12345`。
> 话机没注册，后面所有接听都不会响。

### 工作台 · `/agent`

- [ ] **刚登录，还没签入**
      期望：提示「请签入话机后开始接听」。此时队列不会把电话给你。
- [ ] **点「签入」，再点「示闲」**
      期望：状态变为 *示闲*。班长的坐席页应当同步看到。
- [ ] **看「我的队列」**
      每一行是**你所属的一个队列**，右边是它当前的等待人数（没人就是 `0`）和排在最前那位的等待时长，
      超过**该队列自己的** SLA 阈值才转红。卡片右上角是所有队列的等待总数。
      期望：现在列出 `wt_queue`，等待数 0。**一个队列都不在**时显示「你不在任何队列里，队列来电不会派给你」——
      这两种情况必须分得开。
      备注：2026-08-27 走查时这张卡只列**正在排队的来电**，队列本身不出现，于是「队列很闲」和
      「你根本没被配进任何队列」显示成同一片空白，后者只有等到电话一直不来才会发现。当场改成按队列列出：
      契约里 `WaitingCallList` 加了 `queues`（`StaffedQueue`），坐席拿到自己的、主管拿到全部。
- [ ] **从外面拨打第 20 步那个号码**
      期望：先听到**机器人**用你选的语言问候（不是直接转人工）。让机器人转人工，你的话机才响。
- [ ] **接听后看「当前通话」**
      期望：显示主叫号码与开始时间。若这个号码在客户库里，客户卡片一并显示；不在则显示「尚未识别来电客户」。

      期望：提示「已发送 …」。每按一个键就立即发给对方，不是攒着一起发。

      期望：通话转走，你的腿结束，状态进入话后处理。

## 四 · Bot 能力专项（管理员 · `/admin/bots`）

Bot 是这个产品的核心，所以单列一节。用五个从 java-bot 移植过来的经典用例走查
——它们覆盖了查询、多轮取值、身份校验、外呼回访、催收异议这几类真实业务：

| 流程 | 业务 | 阶段数 | 工具 | 特点 |
|---|---|---|---|---|
| `mobile_support` | 手机售后、查维修进度 | 5 | 1 | 最简单，适合先走这个 |
| `lead_qualification` | 新品回访、销售线索筛选 | 5 | 1 | 外呼场景，多轮取值 |
| `early_collections` | 账单提醒、记录付款安排或异议 | 8 | 3 | 分支最多 |
| `plan_change` | 宽带套餐变更 | 7 | 4 | 有身份校验环节 |
| `field_service_appointment` | 上门服务预约、改期、确认 | 9 | 5 | 阶段和工具最多 |

**怎么把它们放进来。** 文件在 `internal/seed/flows/` 下，打开复制整个 JSON，然后：

**机器人流程 → 新建流程** → 填标识（如 `mobile_support`）和名称 → 进 Designer →
把 JSON 粘进左侧编辑器 → 保存草稿 → 发布。

粘贴本身就是走查的一部分：粘进去就能看到右侧阶段图是否立刻画出来、Tools 和 Persona
两个标签页是否随之有内容。JSON 里的 `id` 和你填的标识是两个独立字段，不要求一致，粘过去不用改。

**HTTP 工具需要业务后端。** 这五个流程都要调接口取事实（查维修单、查账单、约上门），
后端不在时工具会失败——那是对的行为（bot 不该编造），但也就走不完流程。仓库自带一个：

```sh
go run ./cmd/aicc-mockbackend -addr 127.0.0.1:8770
# 然后在 .env 里：AICC_BOT_BACKEND_BASE=http://127.0.0.1:8770
```

它的数据是固定的，所以走查有确定的正确答案：`RMA1001` 在修、`RMA1002` 已寄出、
`92223333` 逾期 8 天共 45.60、`10086002` 在合约期内不能改套餐、`91234567` 已有一个预约。
机器人说的和这些对不上，就是它在编。

### 4.1 载入即校验

v2 是**加载期校验**——写错的东西在 `flowadd` 就被拒，不会等到通话中才发作。
每一条都改坏一处再 `flowadd`，看它拒不拒、错误说不说得清。

- [ ] **算子写错**（`"op": "SORTA_EQ"`）
      期望：拒绝，`phase welcome transition 0: unknown operator "SORTA_EQ"` —— 点名是哪个阶段的第几条转移。
- [ ] **转移指向不存在的阶段**
      期望：拒绝，`... targets "nowhere_at_all", which is not a phase in this flow`。
- [ ] **阶段允许了不存在的工具**
      期望：拒绝，`phase "welcome" allows unknown tool "no_such_tool"`。
- [ ] **`initialNode` 指向不存在的阶段**
      期望：拒绝，`initialNode "missing" is not a phase in this flow`。
- [ ] **删掉 `global.persona`**
      期望：拒绝，`global.persona is empty, so the model has no character to adopt`。
- [ ] **加一个孤立阶段（没有任何转移指向它）**
      期望：**不拒绝，能发布**。这是有意的，见上面第 17 步——由编辑器提醒，不由服务端拦。

### 4.2 Designer 标签页

左边是 JSON 编辑器，右边是阶段图，两边联动。

- [ ] **打开 `field_service_appointment`（9 个阶段）**
      期望：右侧阶段图把 9 个阶段和它们之间的转移都画出来，不重叠、不出框。
- [ ] **在右图点一个阶段**
      期望：左侧 JSON 滚到并高亮该阶段的定义。
- [ ] **把光标放进左侧某个阶段的 JSON 里**
      期望：右图对应的阶段被选中。**双向联动**，不是只有一个方向。
- [ ] **看终止阶段（`finish` / `finish_transfer`）**
      期望：在图上与普通阶段可区分（`isTerminal`）。
- [ ] **故意打错一个字符**
      期望：立刻提示「不是合法的 JSON」，阶段图不崩，保存被拦下。

### 4.3 Tools 标签页

- [ ] **打开 `field_service_appointment` 的 Tools**
      期望：5 个工具都列出：`appt_lookup` `appt_slots` `appt_book` `appt_reschedule` `appt_confirm`。
- [ ] **看任一 HTTP 工具的明细**

- [ ] **确认三个内置工具的呈现**
      期望：`transfer_to_agent`、`take_message`、`hangup` 与 HTTP 工具区分开——它们没有 HTTP 路径，由平台自己实现。
- [ ] **看 `alwaysAllowedTools`**
      期望：转人工和挂断在**每个阶段**都可用，不受阶段允许列表限制。这是设计要求：无论走到哪一步，要人工都不该被挡。

### 4.4 Persona & rules 标签页

- [ ] **打开任一流程的 Persona**
      期望：人设与规则**中英双语都在**，按当前界面语言显示对应的一份。
- [ ] **切换界面语言到 English**
      期望：显示英文那一份，不是中文原文，也不是机器翻译。

- [ ] **看 `maxTurns` 与 `fallbackTarget`**

### 4.5 History 标签页

### 4.6 真的打一通（这一节的重点）

前面五小节都是在看流程长什么样。**bot 的能力最终只有一通电话能证明。**

- [ ] **把 `mobile_support` 绑到一个号码上**
      「号码」页编辑一个可呼入的号码（如 95012），机器人流程选 `mobile_support`，语言中文。
- [ ] **确认 mock 后端在跑**（前置第三项），并且应用是在它之后启动的
- [ ] **用坐席话机拨那个号码**，对机器人说「我要查维修进度，单号 RMA1001」
      期望：机器人**先用中文问候**，问清单号后回答「星讯 X1 手机，维修中，已更换屏幕总成，
      正在整机测试，预计 2 个工作日内寄出」。
      **同时看 mock 后端的终端**：应当打出一行 `/api/repair/status map[rmaNo:RMA1001] → ...`。
- [ ] **对照三件事**
      ① 工具**被调了**（后端日志有那一行）；
      ② **参数对**（`rmaNo` 是 RMA1001，不是听错的别的号）；
      ③ 机器人**照数据说**，没有添油加醋。
      这三件事从电话这头是分不出来的 —— 「问错了单号」和「根本没查」听起来一模一样，
      所以必须看后端日志。
- [ ] **报一个不存在的单号，如 RMA9999**
      期望：后端返回 `found: 0`，机器人如实说查不到，**不编一个进度出来**。
- [ ] **说「转人工」**
      期望：立刻转接，不受当前阶段限制（`alwaysAllowedTools`）。队列没人时应当能转成留言。
- [ ] **挂断后去通话记录看这一通**
      期望：轨迹显示 *机器人 → …*，`bot_sec` 有值；机器人说过的话有转写。

> **想走更复杂的流程**，换绑 `field_service_appointment`（9 阶段 5 工具）：
> 说「我要预约上门维修」，走完预约 → 改期 → 确认三步，每一步后端都会打日志。
> 用手机号 `91234567` 可以走「已有预约」那条分支。

### 4.7 v1 → v2 的能力差异（移植时记录）

这五个流程从 java-bot 的 v1 移植而来，差异如下。它们不是缺陷，是走查时会疑惑的点：

| | v1（java-bot） | v2（本项目） |
|---|---|---|
| 号码绑定 | 流程文件里写 `did: {zh: [...], en: [...]}` | 流程里**没有** did，号码在「号码」页绑定 —— 同一个流程可以被多个号码复用 |
| 挂断工具 | `hangup_call` | `hangup` |
| 留言工具 | 无 | **`take_message`**，且可以「拒绝」——队列关了就转成留言，拒绝是一次对话而不是一个错误 |
| 条件算子 | 只有 `eq` / `gte` | 14 个：`EQ NE GT LT GTE LTE IN NOT_IN CONTAINS NOT_CONTAINS IS_NULL IS_NOT_NULL IS_EMPTY IS_NOT_EMPTY`，且支持 `all` / `any` 嵌套 |
| 音色 | 无 | `global.voice`，随流程发布并版本化 |
| 转移事件 | `on_event: "tool:x"` | `on: "TOOL_RESULT"` + `tool: "x"`，另有 `NO_INPUT` |
| 成功标志 | 后端自定义 | 内置工具统一返回 `{"ok": "1"}` —— **是字符串不是布尔**，写条件时 `"value": "1"` |
| 后端地址 | 流程里 `api_base_env` 指定环境变量名 | **`apiBaseEnv` 字段不生效** —— 地址只来自部署配置 `AICC_BOT_BACKEND_BASE`。移植过来的流程里这个字段还在，是 v1 遗留，存了但没有任何东西读它 |

> **写条件时最容易错、错了还静默的一点**：`result.ok` 的值是字符串 `"1"` / `"0"`。
> 写成 `"value": true` 或 `"value": 1` 不会报错，只是条件永远不成立，转移永远不触发。
> 移植过来的五个流程可以直接当正确写法的样例。

## 五 · 客户 API：第三方系统怎么用这个平台

前四节都在界面上操作。这一节没有界面——它是**客户的系统**通过 API 使用平台的三个能力：
发起外呼、挂断、收 CDR 推送。走查它需要一把 API key。

**前置**：`.env` 里配一把 key 并重启应用（不配则这条路整个关闭，这本身是设计）：

```sh
AICC_API_KEY=$(openssl rand -hex 32)   # 记下这个值
```

下面命令里的 `$KEY` 就是它。

### 5.1 鉴权

- [ ] **不带任何凭据**
      `curl -s -X POST http://127.0.0.1:8080/api/v1/calls -d '{}'`
      期望：**403**，`missing X-AICC-Csrf header`。
- [ ] **带一把错的 key**
      期望：**401**，错误码 `INVALID_CREDENTIALS`（不是 `SESSION_EXPIRED`——机器读到后者
      会去刷新一个从不存在的会话）。
- [ ] **用 key 去读 webhook 订阅**
      `curl -s -H "X-AICC-Api-Key: $KEY" http://127.0.0.1:8080/api/v1/webhook-subscriptions`
      期望：**401**。这把 key 能打电话，但**够不到**「往哪里推数据」的配置——否则泄露一把
      key 就能把全部通话记录导去别处。

### 5.2 外呼与挂断

场景是：**坐席没有登录平台，但话机在线**，客户的系统替他发起外呼。

- [ ] **先让一部话机注册但不签入**（或用主管把该坐席强制签出）
- [ ] **用 key 发起外呼**

      ```sh
      CALL=$(uuidgen)
      curl -s -X POST http://127.0.0.1:8080/api/v1/calls \
        -H 'Content-Type: application/json' -H "X-AICC-Api-Key: $KEY" \
        -d "{\"kind\":\"AGENT_OUTBOUND\",\"to\":\"<外线号码>\",
             \"extensionNumber\":\"<那部话机>\",\"callId\":\"$CALL\",
             \"userData\":{\"ticketId\":\"T-001\"}}"
      ```

      期望：**201**。那部话机**自动摘机**，然后拨对方。坐席没登录也照样能打。
- [ ] **不给 `extensionNumber`**
      期望：**400**，`name the extension to dial from`。key 没有自己的话机，不会替你猜。
- [ ] **给一个从没注册过的分机号**
      期望：**409**，`no such phone`。话机关着的会说 `the phone is not registered`——
      两种是不同的错，一个是集成里写错了号，一个是运维问题。
- [ ] **通话中用同一个 `callId` 再发一次**
      期望：**200** 且 `"isDuplicate": true`，话机**不会被第二次拉起**。
      这是超时重试的保护：客户系统重发不该让坐席的电话再响一次。
- [ ] **用 key 挂断**
      `curl -s -X POST http://127.0.0.1:8080/api/v1/calls/$CALL/hangup -H "X-AICC-Api-Key: $KEY"`
      期望：**202**，两条腿都在一秒内释放。
- [ ] **挂断后看这一通的 CDR**
      期望：`callType` 为 OUTBOUND，**`talk_sec` 与 `bill_sec` 一致**（不是 0），
      `legs` 是 `TRUNK|<对方号码>`，`userData` 里有你传的 `ticketId`。

### 5.3 CDR 推送

- [ ] **起一个能收 POST 的地址**（任何能打印请求的都行，如 `nc -l 9111`）
- [ ] **建一个订阅指向它**（命令见第 24 步）
- [ ] **打一通电话并挂断，等几秒**
      期望：那个地址收到一个 POST，头里有 `Authorization: Bearer <你填的 authToken>` 和
      `X-AICC-Webhook-Id`，body 里 `deliveryId` 与该头**一致**，`revision: 1`，
      `cdr` 是账本里那一行（含 `userData`）。
- [ ] **建一个过滤条件为 `{"callType":["INBOUND"]}` 的订阅，再打一通外呼**
      期望：该订阅**没有任何投递记录**——不是「入队了没发」，是压根没入队。
- [ ] **把订阅地址改成一个不存在的端口，再打一通**
      期望：投递进入重试，Webhook 页能看到尝试次数在涨、最后错误有内容；
      六次之后变 `FAILED`，应用日志里有一条 WARN 点名是哪通电话。

  `params.field`（用户处理器已有这个约定，前端没读）→ `Field` 加错误态 → 每条规则一条文案。
  顺带修掉一处漂移：`web/src/lib/errors.ts` 的注释说后端「从不发成句的话」，而 catalog 发的正是成句的英文。

## 已知的边界

下面这些走查时会碰到，**它们不是缺陷**，走查记录里不必重复登记。

- **中继在交换机侧配置**，界面只读它的状态。
- **质检页未开放**，班长菜单里看不到。
- **不支持会议**，通话控制里该按钮不可用并写明原因。
- **Webhook 只能看不能建**，订阅通过 API 创建。
- **人工通话没有转写**，只有机器人说过的话有（`docs/design/08-transcription.md` D21）。
- **只支持浏览器话机**，硬话机在路线图上。
- **自动应答没有界面开关**，能力在（`agents.is_auto_answer` → `sip_auto_answer=true`），只能走 API 设置。
- **孤立阶段不被服务端拒绝**，由编辑器提醒——运行时它不坏任何东西，通话只是走不到。
- **HTTP 工具需要后端在位**：移植来的五个流程都调业务接口（查维修单、查账单、约上门），
  `apiBaseEnv` 指向的后端不在时，工具会失败而不是编造答案——这是对的行为，但真机打电话
  验证 bot 全流程之前得先有那个后端。

## 怎么记结果

**通过就把 `[ ]` 改成 `[x]`**（VS Code 装 Markdown All in One、Typora、Obsidian 都能在预览里直接点）。

**不通过则保持 `[ ]` 不动**，在那一行下面加一行 `实际：`，写下真正看到的和当时的时间：

```markdown
- [ ] **17. 写一个有孤立节点的流程…**
      期望：服务端拒绝，并点名是哪些节点…
      实际：直接保存成功了，没有任何提示（2026-08-26 15:30）
```

三种状态因此一眼可分，不需要任何非标准语法：

| 样子 | 含义 |
|---|---|
| `[x]` | 通过 |
| `[ ]` + 有 `实际：` 行 | **不通过** |
| `[ ]` + 没有 `实际：` 行 | 还没走到 |

时间要记，通话类问题往往只能靠它去 `logs/aicc-*.log` 里对回来。

- 页面报错：记下错误原文，别只写「报错了」。
- 电话不通：先确认第 22 步的中继在位、话机已注册两件事，再往下判断。
- 数字对不上：记下你看的是哪个统计窗口（今天 / 近 7 天 / 近 30 天）。

统计进度：

```sh
grep -c '^- \[x\]' docs/walkthrough.zh-CN.md   # 已通过
grep -c '^- \[ \]' docs/walkthrough.zh-CN.md   # 未通过或未走到
grep -n '实际：'      docs/walkthrough.zh-CN.md   # 所有不通过项
```
