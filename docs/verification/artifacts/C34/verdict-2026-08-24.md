# C34 闭合留证 — 2026-08-24

## 1. 修复前基线(五个删除接口,全部用不存在的 id)

```
DELETE /extensions/00000000-…  -> 204
DELETE /queues/00000000-…      -> 204
DELETE /dids/00000000-…        -> 204
DELETE /agents/00000000-…      -> 204   ← 立案时未记,本次探针发现
DELETE /queues/00000000-…/agents/00000000-… -> 404
```

**比立案时记的宽**:C34 记了三个,实为**四个**在说谎。
第五个(取消配员)404 只是因为它先查了队列存在与否 —— 队列真实存在、
而坐席根本没配在上面时,它同样回 204。同一个病,只是被一次无关的查询挡住了一半。

契约给这五条**都**声明了 404,所以那一支在四个接口上是**不可达代码**。

## 2. 修复后

```
DELETE /extensions/00000000-…  -> 404
DELETE /queues/00000000-…      -> 404
DELETE /dids/00000000-…        -> 404
DELETE /agents/00000000-…      -> 404
DELETE /queues/00000000-…/agents/00000000-… -> 404
```

正路径未被误伤(建一个真实 DID,删两次):

```
created id=01a03137-fd0c-700f-b33c-67945fbbae76
delete once  -> 204
delete twice -> 404
```

## 3. 修法

五条 sqlc 查询 `:exec` → `:execrows`;`internal/store/catalogstore.go` 新增 `deleted()`
把行数翻译成"那里本来有东西吗";坐席那条用它自己包的词汇(`pgx.ErrNoRows`),
两者各经既有 handler 到 404。**契约一字未改** —— 404 本来就声明好了。

## 4. 测试

- `internal/store/catalogstore_delete_test.go`(需真实 PostgreSQL):
  缺陷本身就是 `DELETE … WHERE id=$1` 匹配不到行时的行为,**没有 fake 能复现**。
  已验证:去掉修复后五个子用例**全部** FAIL。
- `internal/httpapi/catalog_handlers_test.go`:`catalog.ErrNotFound` → 404 的映射,四个接口。

## 5. 影响面核查

`UnstaffQueue` / `RemoveQueueAgent` 的调用方只有 HTTP handler,没有内部对账器;
三个 catalog 删除同样只被 handler 调用,seed 的 `AICC_SEED=fresh` 不走这条路。
故"删不到就报 404"不会打断任何自动流程。
