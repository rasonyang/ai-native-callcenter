## 一、按原样执行:又是一次空窗假通过

```
/reports/me   {"callsHandled":0,"talkSec":0,"wrapUpsOpened":0,"wrapUpsConfirmed":0, …}
cdrs   (今天)  0|0
wrap_ups(今天) 0|0
```

四项"逐一相等",**全是 0**。precondition 写的"wei **今天**至少接过 2 通"
今天并不成立 —— 阶段 3–5 在 08-20/08-21 执行。与 VC-S13-04 同型的 collect 缺陷,
判定不采用本次结果。

## 二、更麻烦的一层:两侧的"当天"根本不是同一天

即使今天有呼叫,这条用例的取证仍然是错的:

| | 当天起点 | 折算 |
|---|---|---|
| 端点 `GetMyDay`(`ledger_handlers.go:102-104`) | `time.Now()` 的**本地**午夜 | 2026-08-22 00:00 **+08** |
| collect 的 psql `date_trunc('day', now())` | DB 时区 = **`Etc/UTC`**(实查) | 2026-08-22 00:00 **UTC** |

**两个边界差 8 小时。** 任何一通 wei 在本地 00:00–08:00 之间接的电话,
端点算进"今天"、collect 算不进 —— 报出来的会是一个**并不存在的产品缺陷**;
反过来也可能**掩盖**一个真的。

讽刺的是这正是本用例 `failure_looks_like` 第一句点名要猎的东西
("差在时间窗的边界"),而缺陷长在**用例自己**身上。
**修法**:两侧都用同一组**显式**边界,不要一边用端点默认、一边用 DB 的 `now()`。

## 四、这条断言**能分辨自己的失败模式**(值得单独记)

`failure_looks_like` 点名了一种"最隐蔽的":`talkSec` 误用 `sum(total_sec)` 而非 `sum(talk_sec)`,
"数字始终偏大且始终看起来合理"。同窗口实测:

```
sum(talk_sec) = 888      sum(total_sec) = 1190
```

**差 34%。** 若实现真犯了这个错,本用例会读到 1190 而不是 888 —— 也就是说,
这条断言是**有分辨力的**,不是那种"无论对错都成立"的空断言。
(对照:本用例原来的 collect 第 1 条口径差 8 小时,反而可能让这个真缺陷躲过去。)

## 五、`wrapUpsOpened=9` 大于 `callsHandled=6`,是对的

逐行查过,**无一重复**(每条 `(call_id, agent_id)` 的 dup 计数都是 1)。9 条的构成:

```
6 条 primary = wei          ← 与 callsHandled=6 吻合
2 条 primary = ben          ← wei 在场但主责是 ben(01a023b2、01a023b7)
1 条 (no primary)           ← 01a023b6-1384,C24 那组里【真实】的那一行
```

两个 CTE 的谓词本就不同:`filings` 按 **`wrap_ups.agent_id`**(谁开的 ACW),
`handled` 按 **`cdrs.primary_agent_id`**(谁是主责)。转接后 wei 开了 ACW 但主责归 ben,
差额由此而来,**两侧各自都对**。expect 未对两者关系做断言,判定不受影响。

**顺带一个观察(非本用例断言,不立案)**:`01a023b6-1384` 是一通 **NO_ANSWER 的
click-to-dial**,它也开了一条 ACW 并计入 wei 的 `wrapUpsOpened`。
"没人接的外拨要不要开 ACW"是产品口径问题,可能是有意的;记此备查。
