# C37 成因调查 — 2026-08-24(七个样本)

材料来自 C7 刚建的读路径 `GET /calls/{callId}/queue-events`。
FreeSWITCH 自己的日志只回溯到 08-23,七通(08-20…08-22)已轮转掉;
用的是 `queue_events`、`agent_state_logs` 与应用日志。

## 一、已确证

### 1. 七通全部是同一部话机 —— wei / 1008,**浏览器话机**

```
01a01e7b  08-20 17:23  22 次  → 807b2164 (wei)
01a021f5  08-21 09:35  13 次  → 807b2164
01a02299  08-21 12:35  23 次  → 807b2164
01a022da  08-21 13:45  23 次  → 807b2164
01a02729  08-22 09:50  33 次  → 807b2164
01a0272c  08-22 09:54  24 次  → 807b2164
01a0272d  08-22 09:56  10 次  → 807b2164
```

**ben 的原生软电话(1002)一次都没有。** 七比零。
这把嫌疑从 mod_callcenter 与应用移到 **web-sip-phone / SIP.js 那一侧**。

### 2. 节奏是成簇的,不是均匀的

```
call          queue        一秒内次数   簇的时刻
01a02729      support-zh      10        09:51:24
01a02729      support-zh      10        09:52:25
01a02729      support-zh       9        09:53:26
01a0272c      support-en      10        09:55:28
01a0272c      support-en      11        09:56:29
01a02299      support-en      10        12:36:08
01a02299      support-en      10        12:37:09
```

**一秒内约 10 次,然后正好 61 秒后再来一簇**,直到主叫放弃。
两个队列节奏完全相同,所以**队列参数不是变量**。
立案时记的"三分钟 42 次、簇内约 70ms"是同一现象的另一种描述,但**结构是簇**。

### 3. 触发条件:一次**被主叫放弃打断**的派单

```
09:49:23  call A  JOINED     support-en
09:49:39  call A  OFFERED    wei        ← wei 刚从 BREAK 转 READY(09:49:39)
09:50:02  call A  ABANDONED  (39 秒)    ← 主叫在派单未解决时挂断
09:50:23  call B  JOINED + OFFERED wei
09:51:24  call B  OFFERED ×10           ← 忙等开始
```

派单**不是被 RONA 超时结束的**,是主叫中途挂断、mod_callcenter 取消了这次 origination。
立案时写的"一次被取消的派单"是对的,这里补上了**取消的原因**。

### 4. 一旦卡住,**跨通话持续**

```
storm         storm_start        前一条队列移动
01a021f5      08-21 09:35:20     01a01ed3 ABANDONED
01a022da      08-21 13:45:54     01a022d9 ABANDONED @13:45:06
01a02729      08-22 09:50:23     01a02728 ABANDONED @09:50:02
01a0272c      08-22 09:54:28     01a02729 ABANDONED @09:53:51   ← 上一场风暴刚结束
01a0272d      08-22 09:54:52     01a0272c OFFERED   @09:54:28   ← 上一场风暴**还在进行**
```

四通紧跟在前一通被放弃之后,一通在**前一场风暴尚未结束时**就开始。
**话机不会在两通之间自愈** —— 是链式的,一次卡死污染此后整个窗口。

### 5. 应用在整场风暴里一个字都没记

`01a02729` 的三分半钟里,应用日志从 09:50:23 的 `sip bye sent` 直接跳到 09:53:51 的 CDR 告警。
派单事件被写进 `queue_events`,但**不打日志**。
运营盯着应用日志看一场风暴,看到的是**静默**。

### 6. 应用侧的坐席状态是**对的**

`agent_state_logs`:wei 09:49:39 由 NOT_READY(BREAK) 转 READY,直到 09:58:30 一直 READY。
不是"镜像漂移把一个不在的人标成可派" —— wei 确实可派,是话机不接。

## 二、新发现:W2.1 的对策**只解决了一半**

`cbf0391`(08-23)下发 `max_no_answer=2 / no_answer_delay_time=60 /
reject_delay_time=60 / busy_delay_time=60`。

`reject_delay_time` 从 0 改成 60,把**一秒十次**变成**一分钟一次** —— 安静了。
**但主叫仍然等不到人**:

**拒绝不是无应答**。mod_callcenter 的 `no_answer_count` 只被"振铃到超时"递增;
一部回 486 的话机永远不递增它,于是 **`max_no_answer=2` 永远不触发**,
坐席**永远不会被置为 On Break、永远不退出轮转**。
(现场 `callcenter_config agent list` 里 agent-wei 的 `no_answer_count` 读作 0。
这是弱佐证 —— 需要一次确认实验,见下。)

所以对策改变的是**噪声频率**,不是**结果**:主叫照样一路听保持音到放弃。
**缺的那一半是**:连续拒绝 N 次的话机应当被当作不可用。

## 三、仍不知道

1. **61 秒这个周期从哪来。** 四个 agent 参数都是 08-23 才写的(`cbf0391`),
   七通发生时它们都是 mod_callcenter 的默认值(均为 0),**没有一个是 60**。
   队列的 `rona_delay_sec` 是 10、`tier_rule_wait_sec` 是 300,也都不是。**未解。**
2. **浏览器话机为什么回 486。** 这是最终成因,仍未查明。
   已知它与"派单被主叫放弃打断"相关,且不会自愈。

## 四、可复现的实验(C37 一直缺的就是这个)

链条给出了配方:

1. wei 的浏览器话机注册、READY;
2. 一通 AI 呼叫转人工进队列 → wei 的话机开始振铃;
3. **主叫在 wei 的话机还在响时挂断**(这一步是关键 —— 制造"被取消的派单");
4. 立刻打第二通进同一队列;
5. 观察 `GET /calls/{callId2}/queue-events` 的 OFFERED 次数。

**判据**:
- 第二通只被派 1–2 次 → 未复现,或 `reject_delay_time=60` 之外还有别的变化;
- 第二通被反复派、且间隔约 60 秒 → **复现成功**,且证实对策只压住了频率;
- 同时看 `callcenter_config agent list` 的 `no_answer_count` 是否仍为 0 → 确认"拒绝不计无应答"。

**对照组**:同一流程改用 ben 的原生软电话(1002)。若不复现,嫌疑就锁定在浏览器话机侧,
而那需要在 `web-sip-phone` 会话里处理(它是另一个仓库,改动走那条路)。
