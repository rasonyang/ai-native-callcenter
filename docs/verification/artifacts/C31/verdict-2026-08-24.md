# C31 / C53 闭合留证 — 2026-08-24

两条是**同一个短缺的两侧**:行在等第二条腿来告诉它号码,而这两型呼叫从来没有第二条腿。

## 1. 修法

- **C31**:`addParty` 原先只给**坐席腿**记 `OtherNumber`。腿面对的是哪个号是**腿自己的事实**,
  与上面坐没坐着坐席无关;而唯一没人可问的那条腿,正是最需要它的那条 ——
  打向本系统不服务的号码,在第二条腿出现之前就被拒了。改为**每条腿都记**。
- **C53**:`aicc_did` 原先只在**桥接到 bot 时**才打到通道上。没人接的呼叫根本走不到那次桥接,
  所以行里既没有被叫号也没有主叫号。改为**置呼那一刻就打在客户腿上**。
  这同时让未接通的外呼拿到"本平台自己置的呼"该有的方向(从 DID 到客户)——
  走的是 C43 已经修好的那个分支,不是新逻辑。

`aicc_did` 打在客户腿上**不会**让它被当成 bot 腿:`isBotLeg` 问的是"这条腿是不是**拨向** DID 的",
而这条拨向的是客户。已由 `TestTheCustomerLegOfAnAIOutboundIsNotMistakenForTheBots` 钉住。

## 2. C31 现场(2026-08-24 01:27)

从我方 external profile 向 `95009`(未配置号码)发起 INVITE,主叫号 18688886669:

```
call_type=INBOUND  from=18688886669  to=95009  did=(空)
status=NO_ANSWER   hangup_cause=UNALLOCATED_NUMBER
```

修复前:全库 11 行 `UNALLOCATED_NUMBER` 的 `to_number` **无一例外为空**。

同窗口另有两行 `OUTBOUND | 95009 → 18688886669` 是**探针方法的产物**
(从本机向本机的 external profile 发起,那是我们自己的去话腿),不是产品缺陷,也不出现在生产形态里。

## 3. C53 现场(2026-08-24 01:28,`01a03161-b16f-79a4-826d-f7362c980bbb`)

`POST /calls {"kind":"AI_OUTBOUND","to":"18688886669","did":"95002"}`,owner 不接,响到超时:

```
call_type=OUTBOUND  from=95002  to=18688886669  did=95002
status=NO_ANSWER    total_sec=0  bill_sec=0  hangup_cause=NO_USER_RESPONSE
```

修复前同一动作产出的是 `from=18688886669  to=(空)  did=(空)` ——
**主叫栏坐着客户、被叫栏空着**,方向也是反的。

## 4. 为什么这两条不是"少了几个字段"

从账本上读,它们长得一样,而处置完全不同:
- 一个停用号被人整天拨 → 要通知客户;有人在**扫号** → 要告警。
- 一次外呼名单**响了没人接** → 要再打一轮;外呼**根本没打出去** → 要修系统。
