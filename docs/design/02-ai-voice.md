# Design 02 — AI Voice Leg (SIP UAS, Audio Bridge, VoiceSession, Flow Engine)

## 1. Voice leg architecture

Per AI call, `internal/aicall` composes three parts around a per-call actor:

```
FreeSWITCH ──INVITE/RTP──► internal/voice (UAS + RTPSession)
                                │ 8k PCM16 frames (rx) / tx queue
                                ▼
                        aicall session actor ◄── internal/flow (engine, tools)
                                │ VoiceSession events/audio
                                ▼
                        internal/provider — one OpenAI-Realtime client × Profile
                        (openai | grok | qwen | any endpoint speaking the protocol)
```

`internal/voice` is the golang-bot port (custom UAS; pion/rtp wire format). Port fixes applied during the port (T4): 200-OK retransmission until ACK (timer G-ish, 500ms×2 backoff, cap 3s), idempotent re-200 on INVITE retransmission, correct `487` CSeq method on CANCEL, no BYE after remote BYE, `a=ptime:20` in SDP answers, `MaxCalls` configurable (default 220), DTMF payload type taken from SDP offer (not hardcoded 101), RFC 3550 §5.1 checklist retained (random SSRC/seq/ts, SSRC collision regen, regen on remote addr change, unknown PT ignored).

One thing the port carried wrong and #250 fixed, invisible here because this topology puts at most one Record-Route on the INVITE: **a UAS's route set is the Record-Route list in the order it appears in the request** (RFC 3261 §12.1.1), and only the UAC reverses it (§12.1.2 — its list came back in a response, where each proxy prepended, so reversing again restores the path outward). The bot's own BYE now carries the set as received, one `Route` header per value however the INVITE grouped them (separate headers, one comma-joined, a mix, or folded over several lines). Reversing walked a two-proxy path backwards, from the proxy nearest the caller toward the one nearest us, so the far end never saw the BYE and the call stayed up until a timer cleared it. `internal/calleesim`, which plays the UAS role too, had pre-reversed the list to compensate and no longer does.

#325 finished the in-dialog path. The bot's INVITE comes straight from the switch on the LAN, so its route set is normally empty and the BYE goes to the INVITE's source, deliberately not the Contact: the source is the address that already reached the bot, while the Contact can carry the address the switch advertises outward (ext-sip-ip). With a route set, the BYE goes to the first entry's address (§8.1.2) when that is a `sip:` URI over UDP to an IP literal; a hostname (never resolved), `sips:`, another transport, IPv6 on the bot's IPv4 socket or an unparseable entry falls back to the INVITE's source with a warning naming the entry. A first entry without `;lr` is a strict router and gets the §12.2.1.1 form: its URI is the Request-URI, the rest of the set follows, and the Contact is the last `Route`. Every BYE carries `Max-Forwards: 70` and a random Via branch; the branch had been the Call-ID's first eight characters. The callee simulator follows the same next-hop rule, with the Contact as its no-route-set destination.

**Ports**: SIP UDP `:6060` (takes over the `aicc_bot` gateway target). RTP pool `40000–40999` (even RTP / odd RTCP pairs → 500 concurrent pairs ≥ 220 MaxCalls with headroom), configurable; deliberately outside FS's 16384–32768 since dev co-locates both on one host.

**Kept from golang-bot verbatim**: 20ms ticker pacing with late-tick resync (no catch-up bursts), TX prebuffer 3 frames (60ms) + 2-tick underrun grace, reorder-only jitter buffer (4-frame window, ≥25-frame gap resync, codec-correct silence fill), RTP dead timeout (5s default), minimal RTCP SR/RR (one-way-dead detection), OPTIONS→200, INFO+RFC2833 DTMF merge, advertise-IP route-probe toward the peer's media address.

## 2. Codec & sample-rate paths (per direction, per provider)

| Leg codec | Direction | OpenAI (preferred: G.711 passthrough) | Qwen |
|---|---|---|---|
| PCMU | uplink | `audio/pcmu` passthrough — **M0-verified** (no resample, no decode) | LUT decode → 8k PCM16 → ×2 linear upsample → 16k PCM16 |
| PCMA | uplink | `audio/pcma` passthrough — **M0-verified** (no transmap needed) | LUT decode → resample as above |
| PCMU/PCMA | downlink | same-law `audio/pcmu` / `audio/pcma` deltas → RTP payload passthrough — **M0-verified** | 24k PCM16 deltas → **windowed-sinc** (32-tap Kaiser) ÷3 decimate → 8k → G.711 encode |
| contingency (OpenAI; retained, not needed per M0) | both | 24k `audio/pcm` both ways: ×3 sinc up / ÷3 sinc down | — |

Rules: all-or-nothing codec wiring per PR#3859's lesson (negotiation → SDP → PT → tables, both laws, with tests); one pre-encoded 20ms silence frame per law (no per-tick zero-encoding); `sync.Pool` for frame buffers, resampler scratch, and base64 buffers (golang-bot's ~5–8 allocs/frame/direction eliminated — the 8c16g requirement's main GC lever); resamplers are fixed-integer-factor (×2, ×3) — linear for upsampling, windowed-sinc for downsampling (java-bot's "muffled TTS" lesson).

## 3. `VoiceSession` — the seam between the call actor and the client

```go
type VoiceSession interface {
    Start(ctx context.Context, cfg SessionConfig) error
    SendAudio(f media.Frame) error            // caller audio, provider-native format (adapter converts)
    SendToolResult(callID string, output string) error // steering rides in output (§6, provider.MergeHint)
    UpdateInstructions(text string) error     // long-call fact pinning / node changes
    SpeakText(text string, isClosing bool) error // say this, now: pre-empts, never queues (§6)
    Interrupt(reason InterruptReason) error   // normalize barge-in (§5)
    Events() <-chan Event
    Close(ctx context.Context) error
}

type SessionConfig struct {
    Instructions string; Voice string
    Language string                            // "en"|"zh" (informs prompts, not routing)
    Turn TurnDetection                         // {Mode: Semantic|VAD, SilenceMs int}
    Tools []ToolSpec                           // JSON-schema tools from the flow
    OpeningText string                         // the call's first words, as written (§6)
    OpeningGate <-chan struct{}                // nil: ask for the first turn now; else wait for close (#98)
    InputFormat, OutputFormat media.AudioFormat
}
```

**Words, not only subjects** (added 2026-09-18). Everything else here is a
brief the model writes from. `OpeningText` and `SpeakText` are the sentence
itself: *say this*. Both are documented as **verbatim where the provider can
manage it and best effort where it cannot** — the client in `internal/provider`
speaks one protocol, and the nearest that protocol comes to handing over words
is a per-response `instructions` telling the model to repeat one sentence and
add nothing. An engine that speaks text outright says it as written, and that
is a property of its profile rather than of this interface.

`SpeakText` is mid-call only, **pre-empts** whatever is being said, and **does
not queue**: a second call before the first has been spoken replaces it, because
both describe what should come next and the older one is by then out of date.
The opening line is `SessionConfig`'s instead, because the first turn is asked
for while the session is being started and there is no mid-call moment to catch
(§4, session bring-up). A turn stopped to make room for a line is reported as
`Interrupted{by: SYSTEM}` rather than `SPEECH`: the consumer must flush its
queue and report played-ms either way — the caller stopped hearing it, and the
provider's history has to be trimmed to what they heard — but it was not a
barge-in, and recording it as one writes an interruption the caller never made
into the log of the call. `isClosing` says the line ends the call (it is set for
a terminal phase's `announce`); a client may steer such a line harder, because
whatever that leaves in the model's history has no later turn to affect. Only
the Realtime client on a profile with `NeedsDirectedLineInConversation` (qwen)
does; the others ignore it.

**`UpdateInstructions` takes effect at once on every client** (issue #13, 2026-10-12; measured 2026-10-15). It is how a fact the flow holds in a slot (`{slots.x}`) and the current phase's instruction stay in front of the model, including after the provider has truncated its own history. The Realtime client sends an instructions-only `session.update` (qwen's silent truncation is harmless to slot state); qwen and openai were measured live (qwen-findings W-Q7, `provider-extension.md`). Doubao sends the whole session body again, tools included, because its tools are a full overwrite; measured live (doubao-findings W-D9): the next reply obeyed the new instructions in every case, 6 of 6 when sent idle and 6 of 6 when sent while the model was still speaking, with tools surviving the overwrite (a style directive was measured, not a recalled fact). By decision (owner, #13) a slot tool's result does **not** repeat the recorded value; the slot stays correct for templates and HTTP tool bodies, which read the engine and not the model.

Events (closed set): `SessionReady`, `AudioDelta{PCM/G711 bytes}`, `InputTranscript{delta|final}`, `OutputTranscript{delta|final}`, `SpeechStarted`, `SpeechStopped`, `ResponseStarted`, `Interrupted{by}`, `ToolCall{call_id,name,args}`, `ResponseDone{status,usage}`, `Error{fatal bool}`, `Closed`.

**What this interface is, and is not** (phase1-decisions A6). It is the seam between `aicall`'s per-call actor and whichever provider client answers, and the place a test stands a fake model. It is **not** the extension point for other kinds of engine. That job belongs one layer down, to the wire protocol: `internal/provider` speaks OpenAI Realtime, parameterised by a `Profile` per vendor of it. A new engine **on that protocol** is therefore a new **profile** — a name, an endpoint, a model, a session dialect — selected by `AICC_PROVIDER` at startup, never a second Go client. That is how the phase-2 **OpenAI Realtime Gateway** (ASR + LLM + TTS behind the same events, in its own service) attaches: as a third value carrying its own endpoint and dialect, impersonating no vendor. **Consequently no recognition, synthesis or cascade concept — type, interface, adapter, placeholder or TODO — ever enters this repo**, in phase 1 or after. The gateway profile itself shipped on 2026-09-02.

**Amended 2026-09-18 — a new protocol, not a new engine.** Only a different wire protocol earns a second client, and `AICC_PROVIDER=doubao` is the first: ByteDance's full-duplex dialogue API, in `internal/provider/doubao`. What makes it a protocol rather than a dialect is lifecycle — a session bootstrapped and confirmed before anything may be sent, no way to ask for a turn, no event for the caller starting or stopping speaking, tool results as items with a role, a close handshake, and an uplink that is a clock and a keepalive at once — none of which is expressible as values in a `Profile`. The seam is unchanged and stays the point: a second client is added **underneath** this interface, produces only events already listed above, and is written in AICC's vocabulary rather than its own. It shares `wsconn`, `provider.Watchdog` and `provider.MergeHint` with the Realtime client because ownership and runtime semantics are identical there, and shares no protocol event, decoder or dispatch, because that is where two protocols are supposed to differ. Which client a name selects is decided in `cmd/aicc/wiring.go` — a sub-package of `internal/provider` cannot be built from inside it — and `internal/aicall` still asks only for a `SessionFactory`. Findings and their evidence: `doubao-findings.md`.

**Amended 2026-09-19, reversed 2026-10-15 — the Gemini client.** A third client, for Google's Live bidirectional API, was admitted on this rule and removed on 2026-10-15 (issue #224): its configuration was fixed at setup, so it could not apply a mid-call instruction change, which every other engine does and which the provider layer now assumes. The record is the archive note `gemini-findings.md`.

## 4. Provider clients

One client per wire protocol, and today there are two: the **OpenAI-protocol client** described in the rest of this section, and `internal/provider/doubao` for ByteDance's full-duplex dialogue API (`AICC_PROVIDER=doubao`, added 2026-09-18 — §3's amendment for why, `doubao-findings.md` for what it rests on). Everything below is the first of them. The second differs in all of it: `session.create` and a confirmation instead of `session.update`/`session.updated`, no `response.create` because the engine answers audio and nothing else, a turn that ends on `output_audio.done` rather than the wire's own `response.done`, a paced uplink that must be muted when the caller's frames stop, and a `session.close` handshake. Both keep the WS hygiene stated below, in shared code where ownership is identical (`wsconn` for dial/write/keepalive/close, `provider.Watchdog` for the two deadlines, `internal/provider/pacer` for the uplink queue and its goroutine) — and both keep **no mid-call reconnect** for the same reason and with the same outcome, a fatal `Error` and a rescued caller.

The OpenAI-protocol client is parameterized by a `Profile` (endpoint, model, auth header, event-name dialect GA/beta, session-field dialect, audio formats) — java-bot's proven shape — plus a thin **Qwen** subtype for DashScope quirks. **Exactly one profile is live per deployment**, resolved once at startup by `provider.ProfileFor(AICC_PROVIDER, …)`: `qwen` or `doubao` inside mainland China, `openai` or `grok` elsewhere, `gateway` for the phase-2 Realtime Gateway (A1; doubao is a separate client, not a profile of this one). Its endpoint and model are defaults, overridable with `AICC_PROVIDER_ENDPOINT` / `AICC_PROVIDER_MODEL` for a proxy, a regional host, or any protocol-compatible server. **Voice is not deployment configuration**: it belongs to the bot, so it is `global.voice` in the flow spec — published and versioned with the persona it goes with (A7). The profile's voice is only the fallback for a flow that names none. Both vendors offer voices that carry Chinese and English equally well, so one bot keeps one voice across a bilingual catalogue rather than switching timbre per call. **Temperature is the same kind of setting**: `global.temperature` (absent = the provider's default; otherwise `0 <= t < 2`, refused at load, the range qwen accepts) is part of the persona and versioned with it. It is useful because free-text tool arguments (`transfer_to_agent.summary`, `take_message.message`) are written by the realtime model, and their variance is otherwise unpinned. Only providers with a field for it send it (qwen; `Profile.AcceptsTemperature`, `docs/provider-extension.md`); the others ignore it and log that once per process. Qwen quirks: strip-and-resend on rejected `session.update` fields, `turn_detection` immutable after first audio (config assembled fully before `Start` sends any frame), event-name folding into the internal enum. M0-verified: endpoint `wss://dashscope.aliyuncs.com/api-ws/v1/realtime?model=…`, `Authorization: Bearer` (env `ALIYUN_API_KEY`), OpenAI-shaped `tools` accepted verbatim — but audio-format fields are never echoed in `session.updated`, so the client must not treat the echo as confirmation.

WS hygiene (mandatory, absent in golang-bot): ping/pong keepalive (15s), read deadlines (45s hard, reset on any frame), single-writer mutex, lazy nothing — connect at call start with a 3s deadline; **no mid-call reconnect** (provider session state is unrecoverable) — a fatal WS error surfaces as `Error{fatal}` → flow `on_error` route (transfer to queue / apology per flow config). Watchdogs: first-audio deadline per response (3s), delta-stall deadline (2s with audio already received → force-complete and play what arrived).

Session bring-up: `Start` = WS dial → `session.update` (instructions, voice, formats, turn detection, tools) → wait `session.updated` → **[Qwen only] synthetic greeting cue** → greeting `response.create` (flow's initial node). ⚠ **M3-verified**: Qwen rejects `response.create` on an empty conversation (`conversation has no messages or no user message`), so the opening turn is prompted with a `conversation.item.create` user text item — a stage direction, never recorded as caller speech. Carried as the profile trait `NeedsCueForFirstTurn` (false for OpenAI, which greets unprompted) with a default cue in the session's language inside the Realtime client.

Where the entry phase names its own opening line (`SessionConfig.OpeningText`, from `announce` in §6), that last request carries it: `response.create` with `response.instructions` set to a say-exactly direction in the session's language, one frame on both dialects — the type discriminator the GA session object needs has no counterpart on a response object. On a `NeedsCueForFirstTurn` provider the direction *is* the cue item as well, because the conversation still may not be empty and a cue saying anything else would steer one turn two ways. With no opening line the request is the bare `{"type":"response.create"}` it always was, byte for byte. Preflight (java-bot pattern): on aicc startup and on config change, a background check dials each configured provider, round-trips one greeting + one tool call, and surfaces status on the admin health panel.

## 5. Barge-in — unified semantics (mandated comparison)

| Step | OpenAI | Qwen | Normalized behavior in aicall |
|---|---|---|---|
| Detect | `input_audio_buffer.speech_started` (server auto-cancels response, emits `response.cancelled`) | `input_audio_buffer.speech_started` (client must act; a response that has sent no audio yet is cancelled by the server, qwen-findings W-Q9) | emit `SpeechStarted` |
| Cancel | already cancelled server-side; client sends `conversation.item.truncate{audio_end_ms=played}` for history accuracy | client sends `response.cancel`; `response.done{status:cancelled}` follows | provider adapter does its dialect; actor sees one `Interrupted` |
| Flush local audio | — (client's job) | — (client's job) | **always ours**: `RTPSession.ClearTx()` drains the TX queue; ~2 frames remain in flight to FS → silence within ~40–60ms. Nothing needs sending to FreeSWITCH (we terminate RTP). Backstop: flush again on `Interrupted` even if `SpeechStarted` was missed (java-bot lesson). |
| Played-time tracking | needed for `truncate` | needed for `truncate` (sent on every Realtime profile, after the cancel) | RTP send loop counts frames per response → `audio_end_ms`; a turn queued but wholly flushed unplayed reports `0` (truncated to 0 and deleted, since qwen ignores the truncate), a turn that queued nothing reports nothing; a response cut short before any of its audio arrived is deleted by the client itself, and when an unheard turn was a tool result's answer the model is told so once in the conversation (qwen-findings W-Q9) |

**Line echo — the failure mode both references hit on real calls (M3, borrowed per owner directive: golang-bot first, java-bot second).** The bot's own voice returns through the caller's handset or speakerphone, the provider's detector calls it speech, and the bot interrupts itself mid-greeting. Two graded mitigations exist in the references:

1. **Barge-in guard window** (golang-bot, `BARGE_GUARD_MS=800`): ignore speech detected within N ms of the bot starting to speak. Cheap, no signal processing, and it covers the common case where the echo arrives at the start of a turn. **Implemented** as `aicall.Config.BargeGuard`, default 800 ms; a keypress is never guarded, because it cannot be an echo of anything. golang-bot's companion heuristic — drop transcripts that are a substring of what the bot just said — does not transfer: in speech-to-speech the interruption fires before any transcript exists.
2. **True echo cancellation** (java-bot `EchoCanceller`, partitioned-block frequency-domain NLMS with Geigel double-talk freeze, 320 ms tail). Live-line evidence 2026-08-05: echo peaked at ~3700 RMS — *above* the floor of real user speech — and the echo is the bot's own words, so neither an energy threshold nor a semantic VAD can separate it from genuine barge-in. Only subtracting an adaptive estimate of the echo from the known playback signal works.

**Deliberately deferred to a later milestone, not overlooked**: (2) needs the far-end signal tapped at the RTP send tick, an FFT, and its own tuning pass, and it is only required where the echo return loss approaches 0 dB. Phase 1 ships (1) and the knob to tune it. The trigger to build (2) is a live call where the guard window proves insufficient — i.e. self-interruption occurring *after* the guard expires.

Turn-detection config mapping: `VAD` → `server_vad` with `SilenceMs` (**the default for both languages**: Qwen's own default 800 ms is lowered to 500 ms — M0-verified as accepted and echoed; OpenAI's GA default is already 500 ms). Semantic turn detection (Qwen `smart_turn` / OpenAI `semantic_vad`) was supported by the provider layer until #225 removed it: no flow field ever chose it, and every call uses `provider.DefaultTurnDetection()` (`server_vad`, 500 ms). M0 found `smart_turn` forces `silence_duration_ms = 2000` and ignores attempts to lower it, i.e. ≈+1.5 s of turn latency — worth it only where backchannel immunity (an "mm-hm" not interrupting) outweighs snappiness. If it is wanted later it comes back with a measured reason; turn detection is frozen after the first audio frame on Qwen, so the choice has to be made before `Start`. DTMF interrupts immediately (policy from golang-bot field data), with one exception: once the call's ending is armed (a transfer or hangup waiting for its closing line) a keypress is recorded (`[keypad] N`, the DIGIT event) but neither interrupts the line nor asks the model for a turn, so the closing line plays out and the armed action runs after the caller heard it, or at the cap. Such a keypress no longer triggers the early run "caller spoke after the closing line"; speech still does.

## 6. Flow engine (DSL v1) over realtime sessions

Spec = **DSL v2**: ui-test's v1 re-keyed to lowerCamelCase per 07 §7 (`specVersion:"v2"`): top-level `id, specVersion, entry, initialNode, global, nodes, tools`; `global{persona, rules, voice, temperature, fallbackTarget, closingTarget, maxTurns, maxTurnsWithoutTool, maxDurationSec, alwaysAllowedTools, apiBaseEnv (parsed, no effect), transitions}`, `nodes{instruction, announce, tools, transitions, isTerminal}`, `tools{kind("http"|"slot"), description, parameters(JSON-schema), http{path, method, body template, successWhen, errorFrom, result slots}, collect{slot, value, when} (http tools: an opt-in list slot, `docs/flow-authoring.md` 2.6.1) | slot, enum (kind slot, below)}` — all user-facing strings bilingual `{en,zh}`; the session uses the entry point's language. The five v1 reference flows are converted by a one-shot script; v1 files stay reference-only.

`announce` (added 2026-09-18) is optional and is the one field of a node that is not a brief: a line the bot says **as written** on entering the phase, rendered with `{slots.x}` exactly as `instruction` is. It exists for the two ends of the range an instruction cannot reach — a closing line a business has signed off, which should not be paraphrased, and an engine that takes no text cue at all, for which a phase whose only job is one sentence has no way to say it. A deployment whose provider is of the second kind sets `Profile.RequiresTerminalAnnounce`, and `flow.RequireTerminalAnnounce` then refuses to **publish** a flow whose terminal phases carry none (422 `TERMINAL_ANNOUNCE_REQUIRED`, `params.nodes` naming them). Publish and not load: the same document is perfectly good where the provider can be cued, and a spec that loads on one installation and not on another would make the dialect a property of the host.

Engine mechanics (java-bot's hint steering, verified live over realtime function calling): the model owns the conversation; the engine owns phase. Node entry → `UpdateInstructions(persona+rules+node instruction)`, then `SpeakText(node announce)` where the node has one — the entry node's goes into `SessionConfig.OpeningText` instead, being spoken before there is a call to speak into. On `ToolCall`: if the tool is not allowed in the current node → `SendToolResult(ok:0 + current-phase hint)`; else run it (HTTP runner: the tool's `timeoutMs`, 5 s by default and 10 s at most, success predicate, slot extraction) and reply with the result, **overwriting `hint` with the next node's instruction** when a transition fires. **The wait line (issue #286, added 2026-10-22):** an HTTP tool runs on a goroutine of its own while the call's goroutine waits for its result. That goroutine owns the runtime until the result is handed back over a channel, so the single-owner rule holds. If the result has not arrived 1 s after the tool started (fixed, not a setting), the call's goroutine says the wait line through `SpeakText`: the flow's `global.toolWaitLine`, or "One moment, let me check that." / "请稍等，我查一下。". It is said at most once per batch and only if nothing is playing: no turn being made or owed, no audio queued, nothing armed. Its turn is marked as an aside (the provider reports it as a spoken line, `IsSpokenLine`), and the turns-without-tool wall, the claim watch and the armed ending all leave it out. The answer's turn comes after the line. The Realtime client owes it past the line's request and asks for it when the line's response ends. A line's turn never calls a tool: qwen answered the line's request with a second call to the tool still running (qwen-findings W-Q8), so the Realtime client never hands out a call made in a line's turn and deletes its item when the turn ends, and on openai the request also carries `tool_choice: "none"`. On qwen the line's direction itself bans a tool call and says the tool is already running (`NeedsToolFreeLineDirection`): the flow's action-claim rule lets "我查一下" be said only with a lookup call, and with the plain direction the line went unsaid. A caller who barges over the line still gets the answer. **Not on doubao** (`Profile.DropsToolResultAfterLine`, doubao-findings W-D10): a line spoken while a tool call is owed starts a new round there, and the result sent afterwards is dropped with no error. Three live calls and `TestLiveDoubaoWaitLine` showed it, so doubao's HTTP tools run without a wait line. The doubao client still holds a set of results that completes while a line it committed is in flight, and sends it when that line's turn ends. The `maxTurns` guard forces the fallback node on runaway tool loops. **Several tools in one response (issue #12, added 2026-09-30):** a model can ask for more than one tool in a single response, and it asked for all of them in the phase it was in. The orchestrator answers each as it arrives, but the engine judges them as a batch, from the first call to the response's `TURN_DONE`: every call is checked against the allowlist, and its result against the rules, of the phase the response was made in, so a first tool's move never gets the second refused. Moves take effect one at a time and the last one wins (the superseded move is logged); a terminal phase reached in the batch is final. The new phase's `announce` is spoken once the batch closes, since a line pre-empts and the response still owes answers until then; the line in a tool result (the engines without `RequiresTerminalAnnounce`) is unaffected.

**Ending a call the model never decides to end (issue #9, added 2026-09-23).** A model that is never told to hang up can be asked "anything else?" forever: a caller's decline is not an event the transition model understands, only `TOOL_RESULT` and `NO_INPUT` are. Two guards close that gap, both keyed off `global.closingTarget` — a terminal node, the flow's own goodbye, that the engine (not the model) can move to on its own:

- **NO_INPUT default.** `NO_INPUT` itself fires after the dead-air timeout, 8 s by default and set per deployment with `AICC_BOT_NO_INPUT_TIMEOUT` (Go duration, 2 s to 60 s, no off; an environment setting, not a flow field), counted from the `PLAYBACK_DONE` of the bot's last word. A silent caller is therefore given up on after about three times that plus the re-prompts. `noInput.count` is *consecutive* silence, not a lifetime total: it resets to 0 on any sign of the caller making progress — a final transcript with words in it (`Engine.OnCallerSpoke`), a keypress (`OnCallerKeyed`) or a tool result (`OnToolResult`). An empty final transcript (noise, echo) neither resets it nor counts for anything else. Where no authored rule could ever fire on `NO_INPUT` from the current phase — matched exactly as `fire()` matches: a rule with no `on` matches every event, and a rule naming a `tool` never matches a silence — and `closingTarget` is set, the engine supplies `noInput.count GTE 3 → closingTarget` itself. A phase with such a rule, however conditioned and whether or not it has tripped yet, is left alone. `on: NO_INPUT` together with a `tool` is refused at load: it can never fire.
- **`maxTurnsWithoutTool`** (int, global, 0/absent = off, negative refused at load) bounds tool-less replies to the caller within one phase — the wall against a tool-less loop ("no", "are you sure?", "no really"). One reply counts when the model *finishes* a turn (`TURN_DONE`, not cut short) that followed a caller utterance with words in it since the last counted turn and made no tool call (`Engine.OnBotTurnDone`). The opening turn, dead-air re-prompts and `announce` turns have no caller utterance behind them and count nothing; a turn that makes a tool call resets the count to 0, as does `OnToolResult` and entering any phase; the turn after a tool-call turn answers the tool's result and counts nothing — which also keeps a caller transcript that the Realtime clients deliver after the tool call from being charged to it. Transcripts that arrive late can therefore only make the wall late by a turn, never early, and two finals for one utterance earn one reply. The wall is crossed when the count **exceeds** the limit — the same "more than" as `maxTurns`. The move is not made then: that reply is still playing, and on qwen a goodbye asked for on top of the provider's own reply was refused, so the call ended with no goodbye. It is made on the `PLAYBACK_DONE` of the crossing turn (`Orchestrator.handlePlaybackDone`), when the floor is free and the caller has heard the reply. Any later `TURN_DONE` re-decides: a caller who talks over the crossing reply flushes it (its playback never completes), and the turn their words produce either resets the count (a tool call) or becomes the reply the move waits for. Setting it above 0 requires `closingTarget`, validated at load.
- **Goodbye without a hangup (issue #147).** The claim check (`claimWatch`) remembers when the last finished bot turn said goodbye in words with no tool call and no armed ending behind it. If the caller then goes quiet, `handleDeadAir` does not ask the model anything (the cue made qwen re-open the call: "are you still there?", a second goodbye, a hangup 22 s late); it moves to `closingTarget` (`Engine.CloseAtUnhungFarewell`) through the same path as the two guards below, and logs it at INFO. A later turn or any tool call takes the claim back. It leaves alone an armed ending, a terminal phase, a campaign call and a flow with no `closingTarget` (those keep the cue).
- Both guards move the call exactly the way any other terminal-phase arrival does — `enterPhase`/`armTheEnding` then the announce, arm-before-speak, the announce asked for with `isClosing`. A closing phase without an `announce` gets a goodbye cue instead (`goodbyeCue`), for the wall as for a dead-air move; without it the model has nothing to answer and the call ends on the 10 s grace cap in silence.
- **Doubao limitation.** The dead-air re-engagement cue is refused there (`ErrTextCueUnsupported`, doubao-findings §5), so a silence produces no bot turn, no playback and therefore no second `NO_INPUT` until the caller speaks: the default never reaches 3 on doubao. An authored `NO_INPUT` rule at `GTE 1` is the only silence rule that can end a doubao call. The wall is unaffected.

**Seed values.** `closingTarget` is set in every shipped flow. No shipped flow sets `maxDurationSec`, so all of them get the 900 s default. `maxTurnsWithoutTool` is set where a closing phase ends in an "anything else?" loop the model can keep running without a tool — `mobile_support` (`repair_report`), `field_service_appointment` (`done_book`/`done_confirm`/`done_reschedule`) and `plan_change` (`submitted`) — and, since #147, in `early_collections`, where a model that has said goodbye in words keeps answering without calling `hangup`. It is left off elsewhere (`novanet_support`, `lead_qualification`), whose conversations have no such loop and gain nothing from a wall that could only cut a legitimate call short. The value is **10**, the same in all four. The wall applies in every phase of a flow, not only the closing one, so it has to sit above the longest tool-less stretch a phase is meant to hold: `mobile_support`'s `welcome` answers usage questions from the model's own knowledge with no tool at all, and a caller working through a settings problem there can reasonably take several exchanges. Ten tool-less replies in one phase is well past that, and in a closing loop it is still a bounded number of "anything else?" — the wall is a backstop for a model that ignores the closing instruction, not the mechanism that normally ends these calls. It is a judgement from reading the flows, not a measured figure.

Authoring rule for a flow's closing phases: after "anything else?", a decline ("no", "that's all") means call `hangup` at once, never ask a second time; a follow-up question or a new request is handled normally, and a request to repeat is honoured. `closingTarget` is the backstop for when the model does not follow that rule, not a replacement for writing it into the phase instruction. A goodbye the model is asked to speak before calling `hangup` is not reliable (issue #147: qwen says it and ends the turn without the call, and the call idles until dead air). A caller speaking over the closing line is not always answering it: with more than `closingTailAck` (1.5 s) of the line still unplayed (measured before the barge-in flush) it is an interruption, the line no longer counts as said, the ending stays armed and the answer's playback (or the re-extended cap) runs it; with less it is the "bye now" that ends the call at once (`callActions.onBargeIn`). A closing line that was never said is owed the same way (issue #207): when a `hangup` moves the call into a terminal phase with an `announce`, a turn with no audio is not the line. It neither runs the armed ending (`onPlaybackDone`) nor counts as the line spoken (`onTurnDone`); a repeated `hangup` with nothing said aloud since arming is refused once with a `CALL_ENDING` hint asking for the line (`refuseHangupWhileLineOwed`, cap restarted), and a second one after that is accepted and ends on the playback of its own turn. A model that never speaks ends at the cap with a WARN, "no closing line". A turn with audio is not automatically the line either (issue #262): when one response ends the call with another tool and `hangup`, the single turn that answers both results often follows the talk phase's instruction ("confirm what you noted") and not the line. `expectClosingLine` keeps the rendered line, the orchestrator forwards the model's final transcripts, and at the `TURN_DONE` of each turn after the arming one `callActions.onTurnDone` holds the words against the line (`saysTheClosingLine`: longest common subsequence of Han characters and Latin words, case, punctuation and emoji ignored, at least 60 % of the line's tokens in order, so a preface or a word of drift passes and a paraphrase does not). A turn that misses is not the line: its audio plays whole, the line is asked for once through the closing `SpeakText` right away (it generates while that turn's tail plays and queues behind it, nothing is flushed), the cap restarts, and the ending waits for the playback of a later turn. This happens even if the missed turn said a goodbye of its own, so a double goodbye is possible; the flow's exact words (a line carrying do-not-call content) matter more, and the farewell patterns of the claim watch are deliberately not used to excuse a paraphrase. The request waits while a later turn is already being made, which may itself be the line. A second miss logs a WARN (`the closing line was not said; ending the call without it`) and the call ends on that turn's playback, with exactly one request per ending. A turn with no transcript cannot be judged and counts as the line. Transfers, limit-decided endings, doubao (`RequiresTerminalAnnounce`) and phases without a line are unchanged. A phase whose job is to close is therefore a terminal phase with an `announce` (the platform arms the ending, then speaks the line), and in a phase where the conversation goes on the instruction is tool-first: call `hangup`, say nothing, the closing line follows. The seeded flows follow both. The rest of the authoring guidance (where business rules, knowledge and long operations belong) is in [`docs/flow-authoring.md`](../flow-authoring.md).

⚠ On a **terminal** node the order within node entry is load-bearing: the ending is armed *before* the line is asked for. Arming records the turn it happened in and fires on the playback of a later one (§6, `PLAYBACK_DONE`), and the line is spoken in a turn of its own — ask for it first and that turn can be the one recorded, after which no playback ever counts and the call ends on the 10 s grace cap with the caller sitting in silence.

**Slot tools and facts the caller states (issue #13, added 2026-10-12).** A slot is durable only if something writes it. Backend response fields did (`result` mapping, `<tool>.<field>`); a fact the caller merely said did not. Three additions, all in `internal/flow`:

- **`kind: "slot"` tools.** A flow-declared tool with `"kind": "slot"`, `"slot": "<name>"`, an optional `"enum": [...]` and a bilingual `description` makes no call: its one argument `value` is stored as `slots.<name>`. The model is told to call it when the caller states the fact; the flow renders it back (`{slots.<name>}` in an instruction or announce, `{slots.<name>}` in an HTTP body) and can branch on it. The model-facing schema is generated (`value`, string, with the enum), so `parameters` and `http` on a slot tool are load errors, as is an unknown `kind`. The latest call overwrites; `<tool>.calls` counts calls; `result.ok` and the usual `TOOL_RESULT` transitions apply, so a recorded fact can move the call (`Engine.RecordSlot` runs before `OnToolResult`). A value is trimmed and its line breaks become spaces (a fact rendered into an instruction cannot add lines to it). **An empty or whitespace-only value, a value over 256 characters (`MaxSlotValueLen`, rejected, not truncated, so half a fact is never recorded), or a value outside the enum is answered with `ok:0` and the reason, and nothing is stored.** A caller who declines a question therefore leaves its slot blank, which is the state an instruction can test and render.
- **Tool arguments are slots.** Every tool call stores its scalar arguments as `<tool>.args.<k>`, replacing the previous call's wholesale (an argument left out this time is not read from the time before). String arguments are cut to 256 characters, because a tool that has already run cannot be refused for what it was given; objects and arrays are not stored.
- **`userData` is seeded.** `flow.SeedSlots(caller, entry, did, userData)` is the one place a call's starting slots are assembled; the business data an outbound call was placed with becomes `userData.<k>` (nested objects flattened with dots, arrays skipped, strings capped). Read-only: the model cannot write userData. A start-of-call lookup (#84) adds its fields here.

**Load-time validation.** A name nothing writes would render as nothing, or never match, and be heard on a call instead of seen in a log, so load rejects `{slots.x}` in an instruction, an announce or an HTTP body, and a transition condition's `slot`, unless `x` is one of: the engine's (`caller`, `entry`, `did`, `lang`, `node`, `turns`, `turnsWithoutTool`, `lastTool`, `noInput.count`), `userData.<k>`, a slot tool's `slot`, `<node>.visits`, `<tool>.calls`, `<tool>.ok`, `<tool>.<field>` where the field is in that HTTP tool's `result` mapping, `<tool>.args.<k>` where `k` is a declared parameter (a slot tool's is `value`), or `result.<field>` for a field some tool maps (`ok` and a transfer's `queue` included). Slot-tool slot names are a single name (letters, digits, underscore), unique within the flow, and never one the engine owns. Persona and rules are not rendered, so they are not checked.

Providers: no per-provider code. A slot is engine state; the model is re-told at once on every engine (§3, "`UpdateInstructions` takes effect at once on every client").

**Built-in tools** (present in every flow's allowed set; not HTTP):

```jsonc
transfer_to_agent: { "queue": "enum(deployment's queues)", "reason": "string (flow-defined category)",
                     "summary": "string (≤600 chars, caller language)",
                     "slots": "object (filled in by the model; the engine's slots are not attached automatically)" }        // → F2 in design 01; all args → userData
take_message:      { "message": "string", "callbackNumber": "string?" }  // → callbacks table + CDR flag
hangup:            { "isFarewellSpoken": "boolean" }                     // ends call gracefully
```

`transfer_to_agent` sequencing: tool call → engine replies with a result whose hint says "tell the caller you're connecting them" → on that response's **`PLAYBACK_DONE`** (or the 10 s cap, `actionGraceCap`) → execute the transfer. ⚠ **Amended in M3**: waiting on `ResponseDone` is wrong — the model finishing generation and the caller finishing hearing are separated by everything still in the RTP send queue (up to seconds), so a transfer on `ResponseDone` cuts the bridge line off mid-word. `aicall` therefore reports the two separately: `TURN_DONE` when the model stops producing, `PLAYBACK_DONE` when the queue has drained and one further frame interval has passed. Anything that must not interrupt the bot — transfer, hangup, goodbye — waits for the second. (golang-bot does the same thing, waiting on `sink.Pending()` before declaring a prompt finished.) ⚠ **Amended 2026-09-30 (issue #24)**: the cap counted from arming cut the line's tail off when the turn carrying the tool call kept speaking after it, because the line queues behind that audio. When a later turn finishes generating uncut, the cap moves to the queued audio's length (`Pending()` × 20 ms) plus `lineDrainMargin` (2 s), if that is later; a provider that never produces the line still ends at 10 s. The cap's warning says which of the two happened: no line generated, or a line generated but not yet heard.

**A transfer can be refused, and the bot handles it in conversation.** Before executing, the engine checks that the target queue exists (or a fallback queue does) and is enabled; otherwise the tool returns `ok:0` with a hint naming the reason (`QUEUE_UNKNOWN`, `QUEUE_CLOSED` — the latter meaning the queue is disabled) and a refusal hint, so the model says something like "we're closed right now — I can take a message" and continues with `take_message`. Business-hours and staffing checks (`NO_AGENTS_STAFFED`) are not implemented. The design places business hours on the queue and not on the DID: an AI-native call center has no separate out-of-hours branch in the dialplan, because the bot has already answered and can simply explain (owner decision 2026-08-13).

## 7. Long-call policy (Qwen 50-turn/300s-audio; OpenAI 60-min)

Tracked per session from usage/turn counts: at **80% of budget** the engine injects a wrap-up steer (via next tool hint or `UpdateInstructions`): summarize, resolve, or offer transfer. At **hard limit** (Qwen: history silently truncates — session survives but memory fades; OpenAI: session ends at 60min): if not terminal, execute `transfer_to_agent(queue=flow.fallback, reason="SESSION_LIMIT")` with the running summary. Fact durability: flow slots live in aicc (not provider history) and are re-pinned via `UpdateInstructions` at each node change, so Qwen's silent truncation never loses structured state. A tool result that stays in the phase but changes what its instruction renders from the slots (a second lookup overwriting `{slots.x}`) re-pins too, ahead of the tool's answer (`Runtime.IsInstructionStale`), so the instruction never quotes a superseded record. Per-flow `maxDurationSec` (default 900) as product-level cap → same wrap-up path.

**Amended 2026-09-29 — the product-level cap is built (issue #10); the provider-usage budget is not.** `global.maxDurationSec` is the one budget: absent is 900, `0` turns it off, anything else must lie between 60 and 3600 (refused at load). It is a wall clock owned by the orchestrator (`internal/aicall/sessionlimit.go`), not the dialplan, so the steer can reach the model, and it counts from the bot leg answering — the same clock as the CDR's `botSec`. Its two clocks are delivered into `drive`'s own loop, because the engine and the runtime belong to the call's goroutine. `null` reads as absent (900), not off. **Doubao:** it takes no text cue, so a flow with no `global.closingTarget` is hung up with no line at the limit; doubao flows should set `closingTarget` (whose terminal phase already must carry an `announce`). This is documentation, not a publish rule (owner decision).

- **At 80%** the runtime adds a platform wrap-up line to the standing instructions (`Runtime.BeginWrapUp`, re-pinned with `UpdateInstructions`): sum up, resolve, or offer a transfer (the offer only when the number's fallback queue is open, since otherwise the limit hangs up and the caller must not be promised a person; else a polite close), within the time left (counted from the limit's deadline at every render, so a later phase change never repeats the figure from 80%), without mentioning the limit. Instructions and not a text cue: the moment is arbitrary, and a cue asks for a turn that would collide with one in progress (refused on the Realtime providers, refused outright on doubao). Every later re-pin keeps the line.
- **At 100%**, if the call is not already ending (nothing armed, phase not terminal) and once the bot has given up the floor (waiting at most `actionGraceCap` for it): the number's own fallback queue, when it exists and is enabled, gets `transfer_to_agent` with `reason=SESSION_LIMIT` and a fixed platform summary (non-empty, because the reason reaches the human path's CDR only beside a summary), and the model is asked for a one-line handover before the armed transfer runs. `flow.fallback` in the text above has no counterpart in the spec — `global.fallbackTarget` is a phase — so the DID's queue is the one queue the platform may pick on its own. A client that takes no text cue (doubao), or a bot that never gave up the floor, is transferred at once. With no open queue the call moves to `global.closingTarget` through the same arm-then-speak path as the turns-without-a-tool wall, or, with no closing target, gets a plain goodbye and a hangup stamped `aicc_bot_finished=SESSION_LIMIT`. When the bot kept the floor past the backstop, no goodbye is asked for on that path either (the cue is a turn the providers refuse): the hangup runs at once, still stamped `SESSION_LIMIT`. A closing phase's own announce is still spoken, since a line pre-empts. Either way the ending is then locked: a `hangup` or `transfer_to_agent` the model issues afterwards reports success and changes nothing.
- **Ledger:** never contained (03-data `is_contained`). A call the bot ends (`global.closingTarget`, the plain goodbye, or the caller hanging up before the handover) is the bot's row, with `hangupCause=SESSION_LIMIT`. A transferred call is the human path's row, which replaces the bot's provisional one: `userData.botReason=SESSION_LIMIT` (beside `botSummary`), and `hangupCause` is the final leg's, saying how the whole call ended, never `SESSION_LIMIT` (#230). No migration: `hangup_cause` is a free string. Counted in `aicc_bot_session_limits_total{outcome=TRANSFER|HANGUP}`.
- **Not built:** a budget computed from provider usage (qwen's 50 turns / 300 s of audio). Slot re-pinning already makes qwen's truncation harmless to structured state, and the wall clock bounds cost on every provider alike.

## 8. Latency budget (target ≤1.2s p50 / ≤2s p95, caller-stop → caller-hears)
