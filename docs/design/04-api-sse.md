# Design 04 — REST API & SSE Contract

Naming per [07-naming.md](07-naming.md): JSON fields lowerCamelCase, enum values SCREAMING_SNAKE_CASE, times `xxxAt` RFC 3339 UTC, durations `xxxMs`/`xxxSec`, booleans `is`/`has`. TS mirrors JSON byte-for-byte. Paths: kebab-case, plural resources; query params camelCase.

## 1. Conventions

Base `/api/v1`, JSON only. Cursor pagination (`?cursor=&limit=`, response `{items, nextCursor}`). Mutations idempotent where it matters (`POST /calls` requires client-minted UUIDv7 `callId`; replay live → 200 snapshot, replay ended → 409). Errors:

```json
{ "error": { "code": "QUEUE_NOT_FOUND", "message": "queue 7005 does not exist", "params": {"queue": "7005"} } }
```
`code`+`params` are the i18n contract — the SPA translates (`errors.<CODE>` keys); `message` is English debug text. HTTP status mirrors class (400/401/403/404/405/409/422/503 `SWITCH_DOWN`/`STORAGE_DOWN`). **The envelope has no exceptions** — a wrong method on a real path answers `405 METHOD_NOT_ALLOWED` in it, and an unknown path under `/api/v1` answers `404 NOT_FOUND` in it rather than falling through to the SPA's index.html, which is what it used to do: a 200 of HTML to an integration that mistyped a path is the worst possible answer, because it looks like success.

## 2. AuthN/AuthZ

`POST /auth/login {username, password}` → argon2id verify → `aicc_session` cookie (HttpOnly, SameSite=Lax, Secure behind TLS), server-side `sessions` row (revocable); `POST /auth/logout`; `GET /auth/me` → user + role + agent profile. CSRF: mutations require header `X-AICC-Csrf: 1` (non-simple request → CORS preflight blocks cross-origin) in addition to SameSite=Lax. Roles no longer gate route groups — see the next paragraph; an account's role decides which scopes its login is granted and nothing more. The map is **derived, not composed**: a role's grant is the union of the scopes of every operation reachable at that rank under the old guards, which is what makes the change behaviour-preserving by construction and every deviation from it enumerable. `docs/auth/scopemap.py` recomputes it from the contract and fails on an unruled one — **AGENT 8, SUPERVISOR 16, ADMIN 20** of the 20 in the vocabulary. Exactly nine deviations exist, all the same one: `config:read` is coarse, so a supervisor who must read queues for the wallboard also reads extensions, numbers, flows, webhooks and the account list. That was ruled on and accepted (there are no credentials in the set — the extension password is `config:write`), and it is a **behaviour change rather than a refactor**, which is why it was not allowed to ride along inside a commit claiming none. SSE auth = same cookie (`EventSource` sends it; dev works via the Vite same-origin proxy).

**Two credentials, one authorization model (2026-08-31)**: a browser presents an HttpOnly session cookie, a system presents `Authorization: Bearer <key>`, and neither is the privileged one. What either may do is a set of **scopes** — `resource:action[:range]`, vocabulary in the contract's root `x-scopes` — and the contract states them operation by operation, in `security`. The server obeys that statement rather than restating it: `scripts/gen-opsecurity.mjs` turns each operation's `security` block into `api.OperationSecurityByRoute`, and one middleware inside the generated wrapper reads the matched route and applies it. There are no role guards on the routing table any more; a role is only the map that turns a login into scopes (`grantedScopes`), and nothing below authentication asks what role anybody has.

A key names the agent it works for in `X-AICC-Agent-ID`; a session may never send that header and is refused `AGENT_IMPERSONATION_NOT_ALLOWED` if it does. The CSRF header is asked of the cookie alone — it exists to protect a credential the browser attaches by itself. Two operations have no bearer alternative at all and say why in the contract: `POST /auth/logout` (a key has no session to end) and `POST /recordings/{recordingId}/reviews` (a score is a person's judgement). A credential with no alternative is answered `401 INVALID_CREDENTIALS`, which is a different failure from `403 INSUFFICIENT_SCOPE` and reads differently to an integration. The old model — one shared `AICC_API_KEY` in the environment, sent as `X-AICC-Api-Key`, reaching two operations as a hard-coded SUPERVISOR — is gone, with no migration path: keys are issued through `POST /api-keys`, each with its own name and scopes.

**The vocabulary is generated, and three assertions hold the model in place.** `x-scopes` at the root of the contract is the only place a scope is defined; `scripts/gen-scopes.mjs` turns it into `internal/api/scopes.gen.go` and `web/src/generated/scopes.ts` — names *and* their one-line descriptions, because a description written by hand in the key-issuing form is a second vocabulary that drifts. The gate is `internal/httpapi/contract_gate_test.go`, running with the ordinary test suite: **(a)** every route `chi.Walk` finds under `/api/v1` is declared in the contract and has at least one credential that can reach it (four registered exceptions with reasons — the three on the metrics listener, and the SPA fallback, which is a consumer of this API and not part of it); **(b)** one error code is spelled the same in the contract, in `internal/httpapi/errors.go` and in both translations; **(c)** an operation reachable by a browser session and by nothing else must be on a whitelist that names why. Each was proved by injecting the defect it exists to catch — a route outside the contract, a deleted translation, a removed exemption — and watching it fail. A passing assertion that was never made to fail is not evidence.

**The contract ships with the binary.** `GET /openapi.json` is unauthenticated and serves the same file this design describes (`docs/embed.go`, `go:embed` — the pattern `web/` already used for the SPA). An integration that has not been issued a key yet is exactly the reader who needs to see what the API offers, and a deployment that answers with its *own* contract cannot drift from a copy somebody downloaded.

## 3. REST surface (method · path · scopes)

**Amended 2026-08-31.** This section used to be annotated *min role*, and it had drifted twice over: it named paths that were never built (`/trunks`, `/trunks/{id}/apply`, `/settings`, `/wallboard`, `/quality/recordings`, `/quality/reviews`, `/audit`, `/agent/wrap-up/extend`, `/flows/{id}/draft|validate|revisions`, `/callbacks/{id}/done|dismiss`, `/reports/agents`, `/reports/dispositions`) and missed ones that shipped. The inventory below is taken from `docs/openapi.json` — **91 operations**, every one of them declaring its own `security` — and the annotation after each group is the scope the contract asks for, not a rank anybody holds. A running deployment serves that contract at `GET /openapi.json`, so this list can always be checked against the thing itself rather than against this file.

Trunks and settings have neither endpoints nor tables any more — both were designed here, never written to, and dropped (00021, 00022). A gateway is defined in the switch's own sofia profile XML and read when that profile loads, so a screen editing a `trunks` row could not have kept its promise; what replaced it is the half that was real, the trunk's **live state read from the switch** and shown in `/system/health`. Settings lost to the same argument in the other direction: every setting this product has is an `AICC_*` variable with `.env.example` as the registry, and a key/value table beside that is a second configuration system. They are named above rather than quietly deleted because a reader who remembers them should find out what happened.

**Auth/session**: POST `/auth/login` (anonymous) · POST `/auth/logout` (**session only** — a key has no session to end) · GET `/auth/me` (authenticated, no scope: "who am I" is not a capability) · GET `/openapi.json` (anonymous — an integration that has not been issued a credential yet is exactly the reader who needs it).
**Agent state**: POST `/agent/login {extensionNumber}` · `/agent/logout` · `/agent/ready` · `/agent/not-ready {reason}` · POST `/agent/wrap-up` — `agent:act`. GET `/agent/presence` · GET `/agent/wrap-up` · GET `/dispositions` — `agent:read`. GET `/agents` (roster + availability) · POST `/agents/{agentId}/force-logout` — `agent:manage`. POST `/agents`, PUT/DELETE `/agents/{agentId}` — `config:write`. **`agent:read` / `agent:act` reach only the subject's own agent identity**; managing somebody else's is `agent:manage`, split out when the derivation's self-check found that a single `agent:*` let an agent read the whole roster and log a colleague out (07 §naming, N1).
**Calls (live)**: GET `/calls` (filters: `queueId`, `agentId`, `callType`) — `calls:read:all`; an agent's own live calls are GET `/calls/mine` — `calls:read:own`. POST `/calls` `{callId?, kind?: "AI_OUTBOUND"|"AGENT_OUTBOUND", to, did?, extensionNumber?, language?, userData?}` (both create `callType:"OUTBOUND"` calls; `kind` left out is `AGENT_OUTBOUND` — decided 2026-09-10) — `calls:create`, **and `calls:create:ai` in addition** when `kind` is `AI_OUTBOUND`. **Shipped 2026-08-26**, and the field list above is the corrected one: the AI leg names a `did`, which is where its flow, language and caller id all come from, rather than the `flowId`/`queueId`/`callerIdNumber` this line first guessed at (m0-findings §AI outbound). Click-to-dial had grown a `/calls/dial` of its own in the meantime; folding it back in is what closed the drift. One route still answers two questions, but the split is no longer a role test in the handler (it read "AI outbound is SUPERVISOR" until 2026-08-31): **the second capability is named in the contract**, so an integration is refused `403 INSUFFICIENT_SCOPE` naming `calls:create:ai`, and a subject that only clicks to dial is never granted it. Whoever has no phone of their own names the `extensionNumber`, and it is checked for registration against the switch rather than against presence. Both kinds are idempotent by the client-minted `callId`. Per-call ops — `calls:control`, **plus an involvement check that is about the call and not about a rank**: POST `/calls/{id}/answer` (→ `uuid_phone_event talk`) · `/hold` · `/retrieve` · `/hangup` · `/mute` · `/unmute` · `/dtmf` · `/transfer {queueId|extensionNumber}` (blind, F2/uuid_transfer) · PATCH `/user-data` (merge-patch). POST `/calls/{id}/monitor {mode: "LISTEN"|"WHISPER"|"BARGE", agentId, extensionNumber?}` — `calls:monitor` (F6). **Shipped 2026-08-29**: the agent leg is named (an internal call has two), and the supervisor's phone is the one they are signed in at as an agent or the `extensionNumber` they name, checked for registration like any other outbound dial. The roster row carries `currentCallId` while `isOnCall`, which is what the request names. The supervisor's leg is stamped `aicc_observer=<mode>` and never `aicc_call_id`: the coordinator drops its events, so it is no party, reaches no stream and no CDR — the audit log has it. Whisper flags are read from the *agent* leg's side: `eavesdrop_whisper_bleg` is heard by the agent, `_aleg` by the far end, BARGE sets both; `eavesdrop_bridge_*` only picks what the supervisor hears and is left alone. One originate per request; changing mode is hang up + ask again.
**Callbacks**: GET `/callbacks?status=` — `calls:read:own`; POST `/callbacks/{callbackId}/claim|complete|release` — `calls:control`. `handled_by` follows the acting agent's user id, never a key id (03 §2).
**Config**: read with `config:read`, change with `config:write` — GET/POST `/extensions`, PUT/DELETE `/extensions/{extensionId}`, GET `/extensions/{extensionId}/password` (**`config:write`, though it is a GET**: it hands back a credential, and reading it is the same act as setting it) · `/queues` (+ GET/PUT `/queues/{queueId}/agents` staffing `[{agentId, level, position}]`, DELETE `/queues/{queueId}/agents/{agentId}`) · `/dids` · `/webhook-subscriptions` (+ GET `/webhook-subscriptions/{id}/deliveries`; 09 §10 — an API key holding `config:write` may configure delivery targets, amended 2026-08-31) · GET `/system/health` (ESL link, PG, provider preflights, trunks, registration count) · GET `/users`. **`config:read` is deliberately coarse** and is one recorded widening: it merges reading queues (supervision's need) with reading extensions, numbers, flows, webhooks and the account list. There are no credentials in that set — the extension password is `config:write` — and splitting out a `queues:read` would open the door to a scope per resource.
**Users**: POST `/users`, PUT `/users/{userId}`, POST `/users/{userId}/password` — **`users:write`, on its own and never folded into `config:write`**: creating an account is the only path to a role, so a leaked `config:write` key changed some configuration while a leaked `users:write` key makes an ADMIN and takes everything.
**Flows**: GET/POST `/flows`, GET `/flows/{flowId}` — `config:read`; PUT `/flows/{flowId}` (draft) and POST `/flows/{flowId}/publish {note}` — `config:write`. Publish is insert-a-revision + point (03 §2); there is no separate validate endpoint, validation runs on the draft write and on publish.
**History & artifacts**: GET `/cdrs` (rich filters + cursor) · GET `/cdrs/{callId}` (detail incl. legs/userData/tech) · GET `/calls/{callId}/queue-events` — `history:read:all`. GET `/cdrs/mine` · GET `/calls/{callId}/transcript` · GET `/calls/{callId}/recordings` · GET `/recordings/{recordingId}/audio` (stream/presign redirect) · GET `/reports/me` — `history:read:own` to reach the operation at all, then **`history:read:all` is the widening**: without it a subject replays only the calls their own agent identity was on, which is the same line `/cdrs/mine` draws (`mayHearCall`). A subject with no agent identity and no `history:read:all` reaches nobody's recording, which is the correct answer rather than an oversight.
**Quality**: GET `/calls/{callId}/reviews` — `quality:review`. POST `/recordings/{recordingId}/reviews` — `quality:review`, **session only**: `quality_reviews.reviewer_id` is a person who can be asked about the score. This is not a UI privilege — a supervisor's cookie reaches it from curl — and it is one of exactly two registered exceptions to "a system can reach what a person can" (§2).
**Reports**: GET `/reports/overview`, `/reports/daily`, `/reports/queues` — `reports:read` (aggregates from `cdrs` + `queue_events` + `agent_state_logs`). An agent's own day is `/reports/me` above, under history rather than supervision.
**Contacts**: GET `/contacts` (`?phoneNumber=` exact match) — `contacts:read`; POST `/contacts`, PUT/DELETE `/contacts/{contactId}` — `contacts:write`. **Their own pair, not part of `config:*`**: a contact is customer data an agent edits between calls, and folding it into configuration would have handed every agent the power to create queues.
**API keys**: POST/GET `/api-keys`, GET/PATCH `/api-keys/{keyId}`, POST `/api-keys/{keyId}/revoke` — `keys:manage`. The secret is returned by the create response and by nothing else, ever; a revoked key is terminal — it stops authenticating, it can no longer be edited (`409`), and it is never hard-deleted (03 §2).
**Audit**: GET `/audit-logs` — `audit:read`. Rows name what authenticated and the agent identity it acted as, so "the CRM put wei ready" is a readable row rather than a null actor with `"api-key"` buried in a jsonb.
**Ops**: `/healthz` `/readyz` `/metrics` — unauthenticated, on the separate `AICC_METRICS_ADDR` listener, declared as an exception in the contract's own description and registered as one in the gate that walks the router (`notTheAPI`).

**Agent workspace (added 2026-08-19)** — the endpoints behind My Calls, Contacts, My queue and after-call work. Every one of them answers about *the caller*, resolved from the credential: none takes an agent id, because an endpoint that did would hand any agent anybody's calls, queues or dispositions. A key acts for an agent by naming them in `X-AICC-Agent-ID` (§2) — which is the same resolution, done once at authentication, and not a parameter these endpoints grew.

| Method · path | Scope | What it answers |
|---|---|---|
| GET `/cdrs/mine` | `history:read:own` | The caller's own finished calls, same filters as `/cdrs` minus the ones that name other people. Each row carries *their* wrap-up. |
| GET `/calls/waiting` | `calls:read:own` | Who is queued in the queues this agent staffs, longest wait first, with the queue's `slaThresholdSec` so a breach is the queue's own promise. |
| GET `/agent/wrap-up` | `agent:read` | The record waiting on this agent — opened when the call ended, with the default disposition — or `204` when there is nothing. This is what a reloaded cockpit reads: the state is the server's, so refreshing is not a way past the confirmation. |
| POST `/agent/wrap-up` `{dispositionCode?, note?}` | `agent:act` | Confirms that record, applying whatever the agent changed, and returns them to READY. **Nothing is required**: the disposition already has a value, and confirming the defaults is a legitimate answer. Accepted after the agent has moved on — the last wrapped call stays addressable until the next one starts — and `409 AGENT_NOT_IN_WRAP_UP` when there is no call to confirm against. |
| GET `/dispositions` | `agent:read` | The wrap-up vocabulary: one flat list of enabled codes, in display order. |
| GET `/reports/me` | `history:read:own` | The caller's own day — calls handled, average handle time, average after-call work, occupancy, and how much of the day's after-call work was confirmed rather than left on its defaults — from the ledger and their presence history. Everything else under `/reports` is supervision. |
| GET/POST `/contacts`, PUT/DELETE `/contacts/{contactId}` | `contacts:read` / `contacts:write` | The customer record book, unique by phone number (`?phoneNumber=` is the cockpit's exact-match lookup). |

## 4. SSE — `GET /api/v1/events`

One stream per credential. A browser opens it with its session cookie (`EventSource` sends it by itself); **a system opens the same stream with `Authorization: Bearer <key>`** — added 2026-08-31, because the product's whole real-time surface is this one stream and a machine client that cannot subscribe to it is left polling REST to guess. Reaching it at all asks for `calls:read:own`. Envelope (cti-server lineage, renamed per convention):

```
id: 48213              ← global seq (hi/lo blocks; gaps after crash are meaningless)
event: PARTY_RINGING   ← type
data: {"version":1,"seq":48213,"type":"PARTY_RINGING","occurredAt":"2026-08-13T07:21:04Z",
       "callId":"…","callType":"INBOUND","partyId":"…","agentId":"…","queueId":"…",
       "payload":{…},"userData":{…}}
```

`callType` (`INBOUND | OUTBOUND | CONSULT | INTERNAL`, Genesys lineage) is present on **every** call event — the agent-facing in/out distinction is envelope-level, never buried in payload, and never changes across transfers.

Event scoping mirrors the domain model — **a Call is an aggregate of Parties**: leg-lifecycle events are party-scoped (`PARTY_*`, `partyId` always set, one event per leg), while aggregate facts stay call-scoped (`CALL_USER_DATA`, `CALL_RECORDING_*`, `CALL_CDR`).

**`userData` vs `switchData` — two concepts, never mixed** (Genesys user-data / Extensions lineage): `userData` is **business** context (`ticketId`, customer fields, AI-collected slots) — RFC 7386 merge-patched via `/calls/{id}/user-data`, size-bounded, survives transfers, lands in the CDR. `switchData` is the narrow Genesys-Extensions equivalent — *a data structure for switch-specific features and information that cannot be described by the other parameters of a request* — and exists in **exactly two places**: the `POST /calls` request (`switchData.sipHeaders` → special `sip_h_*` headers on the new leg; anything expressible as a normal parameter — like origination caller id, which is the first-class `callerIdNumber` field — never goes in `switchData`) and the Lua dialplan scripts when they create/route legs (X-headers, codec pinning, channel variables). It never appears on events, the envelope, the CDR, or any other endpoint. Switch facts that events do need (release cause, SIP status) are ordinary payload fields of those events (`PARTY_RELEASED` payload: `q850Cause`, `sipStatus`); the CDR's technical record is the `tech` column. We deliberately do not reuse Genesys's word "extensions" — in this project `extension` exclusively means a phone extension (07 §7).

Mechanics: 15s `: hb` heartbeat; `Last-Event-ID` resume from the in-memory ring (65,536); older → `SYSTEM_RESET {oldestSeq}` and the client resyncs via snapshots (`/calls` or `/calls/mine`, `/agents`, `/reports/overview`) then re-tails; slow consumers (64-frame buffer full) are disconnected — the publisher never blocks; the HTTP write is the ack. **Scoping is identity-derived, not client-chosen** (fixes cti-server's per-agent-filter gap): a subject with an agent identity receives their own `AGENT_*`, calls they are a party to, their queues' `QUEUE_*`, and `CALLBACK_*` for those queues; **`calls:read:all` is what widens that to every call on the floor** — the handler resolves the scope and hands the hub a `SeesEveryCall` boolean, so the hub never learns that a product with roles or scopes exists (it used to carry an `IsSupervisor` flag, which put a rule about authorization where the authorization code could not see it). A key acting for an agent (`X-AICC-Agent-ID`) is scoped to that agent, exactly as the person would be. `?types=` narrows further (server-side AND).

## 5. i18n error codes

**The set as it stands, 2026-08-31 — 26 codes**, and the contract's `ErrorCode` enum is the source of it:

`INVALID_CREDENTIALS, SESSION_EXPIRED, FORBIDDEN, AGENT_REQUIRED, AGENT_IMPERSONATION_NOT_ALLOWED, INSUFFICIENT_SCOPE, VALIDATION_FAILED(field), USER_DATA_TOO_LARGE, NOT_FOUND(resource), METHOD_NOT_ALLOWED, CONFLICT(resource), EXTENSION_IN_USE, EXTENSION_ASSIGNED_TO_AGENT, LAST_ADMIN, EXTENSION_POOL_EXHAUSTED, AGENT_ALREADY_LOGGED_IN, AGENT_NOT_LOGGED_IN, AGENT_NOT_IN_WRAP_UP, CALL_NOT_FOUND, NOT_CALL_PARTY, OPERATION_NOT_ALLOWED_FOR_CALL_TYPE, USER_SUSPENDED, SWITCH_DOWN, STORAGE_DOWN, RATE_LIMITED, INTERNAL`.

Frontend owns all human wording (en/zh); the backend never concatenates sentences. The initial set guessed at codes that were never needed (`QUEUE_NOT_FOUND`, `FLOW_INVALID`, `FLOW_UNPUBLISHED`, `CALL_NOT_ACTIVE`, `PROVIDER_UNAVAILABLE`, `RECORDING_UNAVAILABLE`, `TRUNK_APPLY_FAILED`) and missed the three the two-credential model needs: **`AGENT_REQUIRED`** (the operation is about an agent and this subject has no agent identity), **`AGENT_IMPERSONATION_NOT_ALLOWED`** (a session sent `X-AICC-Agent-ID`), **`INSUFFICIENT_SCOPE`** (authenticated, and naming the scope that was missing — a different answer from `401 INVALID_CREDENTIALS`, which is what a credential with no alternative gets).

**The four spellings are held equal by a test, not by care** (`TestOneErrorCodeIsSpelledTheSameEverywhere`): the contract enum ≡ `internal/httpapi/errors.go` ≡ `web/src/locales/en` ≡ `web/src/locales/zh`. `errors.go` is hand-written, so the assertion parses it with `go/parser` rather than comparing against a transcribed list — a check that guards its own copy of the thing guards nothing. Two keys are registered exemptions with reasons (`UNKNOWN`, `rules`), and a second assertion watches that they are still there: a vanished fallback would make the interface print raw keys while the alignment test kept passing.
